# 反脆弱性・脱固定化・可逆性は新シンプルルール集ではなく rules 層 + 出口コスト台帳で取り込む

## 背景・当時の前提

- fladdict の記事「[Q. どのAIモデルがいいですか？](https://note.com/fladdict/n/n8988752e2713)」を受け、ユーザーが「開発用のシンプルルールを別途作成して反脆弱性・脱固定化・可逆性を Fable に意識させる」案を提示した
- 記事の主張: モデル・ベンダーの選定の巧拙より「ダメになった時にすぐ捨てられること」を重視せよ。固定費を下げる、小さく試してから広げる、アセットを分割する、単一手段に固定しない、疎結合化する
- 検討時点で記事の核は既に判断層にあった:

| 記事の主張             | Dayopt での実装済みの姿                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 可逆性                 | シンプルルール 4「不可逆だけ遅く、可逆は速く」+ テンポ制度 + Reversibility Table                                   |
| 脱固定化               | ルール 5「2 週間触らなかった機能は削除候補」+ 月次ガーデニング                                                     |
| 小さく試してから広げる | plan-format.md の Minimum Viable Approach                                                                          |
| 疎結合化               | feature-boundaries.md（lint:boundaries で機械強制）、「AI は外にいる」「参照するが、所有しない」（strategy.md §4） |
| 固定費を下げる         | workflow.md §なぜ束ねるか（CI 課金の固定費分析）                                                                   |
| AI モデルに固定しない  | ai-behavior.md の tier 読み替え原則                                                                                |

## 決定と理由

1. **独立した「開発用シンプルルール集」は作らない**
   - シンプルルールが効くのは同じ型の判断が繰り返し来る場所。技術・ベンダー選定は個人開発では低頻度で、使われないルール集は月次ガーデニングの検証で官僚化として削除候補になる
   - 開発層の可逆性は既に機械で強制されている（Reversibility Table、pause point）。ヒューリスティック層が要るのは機械化できない判断だけ
   - ルール作り自体に「小さく試してから広げる」を適用する
2. **本当に欠けていた出口コスト観点だけを最小で入れる**
   - `.claude/rules/code-style.md` §依存関係の追加 にチェック 5（出口コスト）と §技術選定スタンス を追加
   - `docs/engineering/infra.md` §出口コスト台帳 を新設。既に深く浸透した依存（Supabase が唯一の最深部）の浸透・逃げ道・出口検討トリガーを可視化する。**乗り換え準備ではなく防災マップ**
3. **記事のフレームに足りない 5 要素を記録する**（今回の議論での Fable の分析。将来の再検討の起点）
   - **検知**: 可逆性は「気づいた者」しか行使できない。台帳のトリガー列がこの実装
   - **何を不可逆に固定するかの選択**: 信頼・約束は固定するから複利で増える。strategy.md §5「変えないもの」があのリストの対になる
   - **復旧可能性 ≠ 可逆性**: 判断は戻せても事故は戻らない。全体復元の演習は未実施（→ 影響・やること）
   - **上振れへの露出**: 記事は守り一辺倒。MCP 正典ポジションのような損失上限つきの賭けと、差別化の核でコミットする勇気が反脆弱性のもう半分
   - **人間が最大の分割不能アセット**: ソロ開発では創業者の健康と意欲がすべてのオプションの原資
4. **人間 SPOF の緩和方針を明文化する**
   - 「User が動かなければ何も動かない」状態を、①知識の repo への外部化（docs 規律、継続）、②定型運用の skill / Routine 化で「Fable に依頼すれば動く」状態の維持、③委任不能コアの明示的な最小化、で緩和する
   - **委任不能コア**（User にしか出来ないこと。これ以外は原則 Fable へ委任可能に保つ）:
     - 価値判断と権限: CHECKPOINT / EXPLICIT AUTHORITY の裁可、production mutation・課金・release の最終承認
     - 一次情報: 自分の 1 日・体験の違和感（ルール 1 のセンサー）
     - 所有: アカウント・支払い・秘密鍵（1Password）・法的責任
   - codebase 全体の把握・検証のような Fable が優位な領域は Fable を正とする（CLAUDE.md §協働のかたち の再確認）

## 却下した選択肢と、なぜ捨てたか

- **開発用シンプルルール集の新設** — 上記 1 の理由。ただし昇格条件を残す: 技術選定判断が頻発し、台帳・スタンスの参照実績が数ヶ月続いたら、シンプルルール層への昇格を再検討する
- **CLAUDE.md の 5 箇条への追記 / 6 個目の追加** — ルール 4 が既に核を担っており、6 個目は「どれかを削る」原則に反する
- **月次ガーデニングへの固定費（サブスク）棚卸し追加** — 請求データは User 側の一次情報で Fable が検証できず形骸化する。サブスクが増えて痛みが出たら再検討
- **Supabase の adapter 層化** — 「念のため abstraction」で plan-format.md が却下する over-engineering。現ステージの正解は乗り換え可能にすることではなく、乗り換えコストを知っていること

## 影響・やること

- `.claude/rules/code-style.md` と `docs/engineering/infra.md` の変更は本決定と同じ PR に含める
- 全体復元（backup / PITR からの restore）演習の issue 化を User に提案する（2026-07-08 の migration drift ログに「backup / PITR 状態を確認する」と残ったまま演習未実施。テストしていないバックアップはシュレディンガーのバックアップ）
- 委任不能コアの運用（どこまで Routine / skill 化が進んだか）は月次ガーデニングの観察対象とする
