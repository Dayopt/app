## 1. なぜ作るか（原体験）

- Google カレンダーを何年も使ったが、**記録するだけで意味が生まれなかった**。「それだけになっててよく分からない」状態。入力も面倒だった
- 最初は ClickUp のようなタスク管理（ボード・テーブルビュー）を作ったが、**違った**。必要なのは 3 ステップくらいで簡単に予定が立てられて、かつ**抽象的でいい**こと
- 例: 「開発」タグの下に「API」がある。それを押して「2時間やった」で基本的に終わり。詳細（仕様書・成果物・タスクの中身）は GitHub Issues や Notion にあり、Dayopt が持つ必要はない。必要ならリンクを貼ればいい
- だからタスク管理ツールとの併用が前提。創業者自身、GitHub Issues をやめる予定はない

## 2. ジョブと売り物

```
ジョブ        : 計画を守れるようにする（「計画を守れない」を解決する）
手段          : 予定と実績を 1 つのタイムラインに重ね、ズレを理解できるようにする
得られる価値  : 進捗感（進んでいる感覚）と「自分を高めている」感覚 — これが続ける理由になる
```

**「ズレを見せる」は手段であって売り物ではない。** 誰も朝起きて「自分のズレが見たい」とは思わない。欲しいのは「立てた計画がその通りに進む日」。ズレはそこへ至るための計器。

> **一文コンセプト: Dayopt は、予定と実績のズレを毎日の学習に変え、「守れる計画」を立てられるようにする、いちばん軽いタイムボクシングツール。**

英語の約束: **"Plan days you can actually keep."**

使い続けると起きること: 作成時に統計が「30分の予定だが、この作業の実績は45分」と教えてくれる → 見積もりを直す → 計画が守れるようになる → 見積もり精度が上がっていく。

## 3. ターゲット

**AI を使いこなす知的労働者。** タスク管理や情報整理はすでに AI や既存ツール（GitHub Issues / Notion / Slack）に任せていて、自分の時間の全体感を見る場所がない人。開発者はその中核だが、開発者に限らない。創業者自身がアーキタイプユーザー。

- 市場は世界中の個人。B2B ではない
- この人たちは Claude / ChatGPT のチャット画面で、複数の MCP（Notion、Slack、そして Dayopt）を横断して「他にやった方がいい活動ある？」「うまい使い方ある？」と聞く。**横断的な考察はチャットでやるのが自然**であり、Dayopt の中に AI チャットは要らない
- Dayopt の役割は、その会話を可能にする**構造化された時間データの正典（source of truth）**であること

## 4. プロダクト原則

1. **参照するが、所有しない。** Dayopt が所有するのは時間とタグだけ。タスクの詳細・成果物・メモの本体は他ツールの領土で、リンクで参照する。詳細を持たないから 3 ステップで予定が立つ
2. **エントリは抽象でいい。タグが語彙。** 入力の最小単位はタスクではなくタグ（2階層: `開発:API` 等）。タイトル欄は存在しない。あるのはタグ + 一言メモ欄（リンク貼付可）だけ。3階層以上や自由なメタデータは分類管理という新しい摩擦を生むので許さない
3. **自動生成はゴーストまで。確定は人間のワンタップ。** ルーティン（繰り返し）、AI の書き込み（MCP/API 経由）、外部カレンダーの予定 — どこから来ても未確定のゴーストとして現れ、クリックで実際のエントリになる。無視すれば消える。この単一概念で「自動化の便利さ」と「選択型ログの主体性」を両立する
4. **記録の確定は人間の儀式。** 自己記録の効果（達成感・行動変容）は人間の手で確定するから生まれる。API は書き込みも開けるが、UI 設計は常に「人間の 1 タップ確定」を最短経路に置く
5. **データの正直さを壊さない。** 予定は時間が流れたら凍結（後から書き換えたらズレが捏造できてしまう）。ただし記録（実績）はいつでも追記・訂正できる。開始直後の予定変更には短い猶予を設ける
6. **進捗は報酬ではなく証拠で見せる。** バッジ・点数・ストリーク演出はしない。「このタグの見積もり精度、4週間前より上がっています」「先週守れなかった計画が今週は守れました」という過去の自分との事実比較だけが進捗感の源泉。比較対象は常に過去の自分
7. **通知はユーザーの計画に仕える。アプリの都合で鳴らさない。** ブロック開始・終了の合図（opt-in）は「自分が頼んだ合図」であり OK。streak 煽り・離脱メール・re-engagement push は永久に禁止
8. **AI は外にいる。** in-app の AI 機能は作らない（少なくとも初期は）。MCP / API であらゆるデータを読み書きできるようにし、ユーザーが自分の AI（Claude / ChatGPT）を接続する。統計的なフィードバック（見積もり実績の提示、週次の補正提案）はルールベースの計算で十分成立し、AI を必要としない
9. **軽い・早い・少ない。** 速度・起動の速さ・操作数・画面の少なさは機能要件。Sunsama を重さで、Motion を「勝手に動かされる不信」で相対化するための武器

## 5. 体験の骨格

### 計画する

- タグを押して時間に置く。3 ステップ以内で完了
- ルーティン（繰り返し設定したエントリ）は当日にゴーストとして現れ、ワンタップで確定。確定されなかったルーティンもズレデータになる

### 実行する

- ブロック開始・終了の opt-in 通知が合図をくれる（フローに入った人間は時間感覚を失うので、これがないと計画は朝作った飾りになる）
- 記録はワンタップ。押し忘れは後から自由に訂正できる

### ズレを見る（レビューページは作らない — 3点に分散する）

1. **カレンダー上のオーバーレイ** — 予定と実績が同じタイムラインに重なって見える。操作ゼロのレビュー。1 Entry モデルの視覚的ペイオフであり、LP のスクリーンショット 1 枚で差別化が伝わる絵
2. **サイドパネル** — 今日/今週の差分、タグ別の詳細分析。「この作業は予定と記録が1時間ずれている」が分かる場所。1 画面で終わる読み物以上にはしない（レポート機能を作り込むと Toggl/RescueTime の領土に入る）
3. **作成時のフィードフォワード** — ブロックを置く瞬間に「30分の予定ですが、このタグの直近実績は45分です」と統計が静かに教える。学習が一番転移するのは振り返っている時ではなく次の計画を立てている時。過去を責める表示ではなく、未来の入力を助ける表示

### つながる（AI・外部ツール）

- MCP / API で全データを読み書きできる。ユーザーのチャット画面で「今これやってるからタグで2時間つけておいて」が動く
- API の書き込みはデフォルトでゴースト経由（§4-3）。直接確定の許可は要検討（§9）
- 週次にルールベース統計で「来週の 1 つの補正」を提示する（AI 不要）

## 7. 変えないもの

1. **1 Entry モデル**（[ADR-001](../architecture/adr/001-unified-block-model.md)） — 計画と実績を同じ物体に重ねる設計は本物の差別化
2. **Todo エンジンを作らない** — サブタスク・優先度・期限・ボード・テーブルは作らない（一度作って捨てた）
3. **他人と比較しない・gamification をしない**
4. **$5 価格帯** — 「AI と連携できて、全体感が見えて、カレンダーと紐づく」なら $5 は払う。$10-20 だと微妙。この感覚を維持する
5. **軽さ・速さ・少なさ**

## 8. v1「完成」の定義

機能が揃ったら完成ではない。**このループが最小摩擦で 7 日間自走したら v1 完成:**

1. 朝（または前夜）: ルーティンのゴースト確定 + 数ブロックの計画が **2分以内**
2. 日中: ブロック開始の合図が来る。記録はワンタップ、押し忘れは後から訂正できる
3. 夜: カレンダーを開いた瞬間、今日の予定と実績の重なりが見える（操作ゼロ）
4. 週末: ルールベース統計が「来週の 1 つの補正」を提示する
5. この間、アプリの都合の通知・煽りがゼロ

残作業リストは「このループの欠けと摩擦」だけで構成する。あったら良い機能はリストに入れない。
