# 機能スコープ: やらないことを決める（繰り返し・通知・習慣・ポモドーロ等を採用しない）

## 基本情報

- **決定日**: 2026-06-16
- **決定者**: 創業者
- **ステータス**: 承認済み
- **カテゴリ**: プロダクト

## 決定事項

### 概要

Dayopt は「機能数」で競合（TickTick 等の all-in-one タスク管理）と戦わない。**明確にやらないことを決める**ことを差別化の核とする。タイムボクシング × 時間記録 × タグの一体化に集中し、隣接カテゴリの定番機能を意図的に採用しない。

### 採用しない機能

| 機能                   | 採用しない理由                           |
| ---------------------- | ---------------------------------------- |
| 繰り返し予定（Repeat） | 「予定と実績の差分を見る」体験と衝突     |
| 通知での追い立て       | 「通知で追い立てず差分を見る」方針と衝突 |
| 習慣トラッカー         | 別プロダクトの領域                       |
| ポモドーロ             | Dayopt の核ではない                      |
| Kanban                 | タスク管理に寄りすぎる                   |
| ToDo 管理全般          | GitHub Issues 等と役割が被る             |
| Eisenhower Matrix      | 優先度管理に寄りすぎる                   |

### 繰り返し予定の具体的経緯

繰り返し予定は一度スキーマに存在した（`entries` の `recurrence_type` / `recurrence_rule` / `recurrence_end_date`）が、本番に繰り返しエントリが存在しないまま [`20260319130001_remove_recurrence.sql`](../../supabase/migrations/20260319130001_remove_recurrence.sql) で列ごと削除した。Google カレンダーは繰り返しを前提とするが、Dayopt は「毎回その日の時間を選び取る（選択型ログ）」体験を優先し、繰り返しによる自動生成を持たない。

## 背景・理由

### なぜ「やらないこと」を決めるのか

競合分析（[`docs/strategy/research/competitors/`](../strategy/research/competitors/)）の結論は明快だった。TickTick は機能量・価格・対応プラットフォームで非常に強く、**Dayopt は機能数では勝てない**。勝ち筋は all-in-one を目指さず、時間の使い方を整える 1 点に絞ることにある。

```
TickTick = ToDo / カレンダー / ポモドーロ / 習慣 / 統計をまとめる all-in-one app
Dayopt   = タグを時間に置き、予定と実績の差分で明日を補正する timebox tool
```

機能を足すほど「全部入りの劣化版」に近づく。採用しない機能を明文化することで、実装判断・LP のメッセージング・Pro の価値訴求（機能量ではなく核心 UX / MCP / API に寄せる）が一貫する。

### コピーライティングとの整合

避けたい表現（「ToDo も習慣もポモドーロも全部管理」「リマインダーで忘れない」「生産性オールインワン」）と、使いたい表現（「Todo ではなく、時間を整える」「通知で追い立てず、予定と実績のズレを見る」）は、この非採用方針から導かれる。詳細は [`.claude/rules/copywriting.md`](../../.claude/rules/copywriting.md)。

## 検討内容

### 再評価の条件

非採用は固定ではないが、追加する場合は「Dayopt の核（予定と実績の差分）を強化するか」を基準にする。単に競合にあるから・要望があるからでは足さない。特に注意:

- **繰り返し**: 外部カレンダー同期を実装する場合、外部由来の繰り返しイベントの取り込み可否を別途設計する必要がある（時間重なり禁止とも衝突しうる。ADR-018 参照）
- **通知**: 現状のリマインダーは最小限のトグルに留める。プッシュで追い立てる方向には拡張しない
