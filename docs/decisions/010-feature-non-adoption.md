# 機能スコープ: やらないことを決める（習慣・ポモドーロ等を採用しない。繰り返し・通知は条件付き採用に改定）

## 基本情報

- **決定日**: 2026-06-16（2026-07-02 [`docs/strategy/concept.md`](../strategy/concept.md) 策定に伴い、繰り返し予定・通知の扱いを改定）
- **決定者**: 創業者
- **ステータス**: 承認済み（一部改定）
- **カテゴリ**: プロダクト

## 決定事項

### 概要

Dayopt は「機能数」で競合（TickTick 等の all-in-one タスク管理）と戦わない。**明確にやらないことを決める**ことを差別化の核とする。タイムボクシング × 時間記録 × タグの一体化に集中し、隣接カテゴリの定番機能を意図的に採用しない。

### 採用しない機能

| 機能              | 採用しない理由               |
| ----------------- | ---------------------------- |
| 習慣トラッカー    | 別プロダクトの領域           |
| ポモドーロ        | Dayopt の核ではない          |
| Kanban            | タスク管理に寄りすぎる       |
| ToDo 管理全般     | GitHub Issues 等と役割が被る |
| Eisenhower Matrix | 優先度管理に寄りすぎる       |

### 条件付きで採用する機能（2026-07-02 改定）

| 機能                   | 現在の扱い                                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 繰り返し予定（Repeat） | **提案型ルーティンとして採用**。ルーティンは当日にゴーストとして現れ、ワンタップで確定。全自動生成・自動確定は引き続き非採用。詳細は [concept.md §4-3/§5](../strategy/concept.md)                       |
| 通知                   | **計画に仕える opt-in 通知は採用**（ブロック開始・終了の合図）。アプリの都合による通知（離脱メール・re-engagement push・streak 煽り）は引き続き非採用。詳細は [concept.md §4-7](../strategy/concept.md) |

### 繰り返し予定の具体的経緯

繰り返し予定は一度スキーマに存在した（`entries` の `recurrence_type` / `recurrence_rule` / `recurrence_end_date`）が、本番に繰り返しエントリが存在しないまま [`20260319130001_remove_recurrence.sql`](../../supabase/migrations/20260319130001_remove_recurrence.sql) で列ごと削除した。

2026-07-02 の concept.md 策定により、この判断を改定した。理由: 現実の1日の相当割合は繰り返し構造（standup、ジム、週次レビュー等）でできており、それを毎朝手で置き直させるのは「最小摩擦」の自己矛盾だった。また外部カレンダー同期は必然的に繰り返しイベントを持ち込むため、全面非採用は同期実装時点で破綻する。「毎回その日の時間を選び取る（選択型ログ）」体験は、**自動生成はゴーストまで・確定は人間のワンタップ**という形で維持する（自動確定はしない）。

## 背景・理由

### なぜ「やらないこと」を決めるのか

競合分析（[`docs/strategy/research/competitors/`](../strategy/research/competitors/)）の結論は明快だった。TickTick は機能量・価格・対応プラットフォームで非常に強く、**Dayopt は機能数では勝てない**。勝ち筋は all-in-one を目指さず、時間の使い方を整える 1 点に絞ることにある。

```
TickTick = ToDo / カレンダー / ポモドーロ / 習慣 / 統計をまとめる all-in-one app
Dayopt   = タグを時間に置き、予定と実績の差分で明日を補正する timebox tool
```

機能を足すほど「全部入りの劣化版」に近づく。採用しない機能を明文化することで、実装判断・LP のメッセージング・Pro の価値訴求（機能量ではなく核心 UX / MCP / API に寄せる）が一貫する。

### コピーライティングとの整合

避けたい表現（「ToDo も習慣もポモドーロも全部管理」「リマインダーで忘れない」「生産性オールインワン」）と、使いたい表現（「Todo ではなく、時間を整える」「通知で追い立てず、予定と実績のズレを見る」）は、この非採用方針から導かれる。詳細は [`.claude/rules/copywriting.md`](../../.claude/rules/copywriting.md)。

## 検討内容

### 再評価の条件

非採用は固定ではないが、追加する場合は「Dayopt の核（計画を守れるようにする、予定と実績の差分を理解する）を強化するか」を基準にする。単に競合にあるから・要望があるからでは足さない。特に注意:

- **繰り返し（提案型ルーティン）**: 外部カレンダー同期を実装する場合、外部由来の繰り返しイベントもゴーストとして取り込む（時間重なり禁止とも衝突しうる。ADR-008 参照）。ゴーストの有効期限・`confirmed` フラグの実装形式は未確定（[concept.md §9](../strategy/concept.md)）
- **通知**: opt-in のブロック開始・終了合図のみ。プッシュで追い立てる方向（離脱メール・re-engagement push）には拡張しない
