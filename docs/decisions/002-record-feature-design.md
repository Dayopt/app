## 決定事項

### 概要

Dayoptの「選択型ログ」を実現するRecord機能の設計を、Claudeとの壁打ちを通じて決定した。

### 決定内容

| 項目           | 決定                                 |
| -------------- | ------------------------------------ |
| DBテーブル     | Plan / Record は別テーブル           |
| リレーション   | Plan : Record = 1 : N                |
| plan_id        | nullable（独立Record許可）           |
| 必須フィールド | タイトル、開始時刻、終了時刻         |
| 任意フィールド | メモ、満足度(1-5)、タグ              |
| タグ           | PlanとRecordで共通のタグマスタを使用 |
| 重複           | 同一時間帯に複数Recordは不可         |
| 日跨ぎ         | 基本不可（睡眠のみ検討）             |
| 編集           | いつでも可能、Activity（履歴）で追跡 |

## 背景・経緯

### なぜRecord機能が必要か

Dayoptのコンセプトは「選択型ログ」。

```
Plan    = これからやること（予定・意図）
Record  = 実際にやったこと（実績・ログ）
```

この2つを対比することで：

- 予定通りにできた/できなかったの振り返り
- 実際の時間の使い方の可視化
- 満足度の傾向把握

を実現する。

### 既存ツール（Toggl等）との違い

壁打ちの中で「タイムトラッカーと何が違う？」という問いが出た。

**差別化ポイント**:

- PlanとRecordを同じアプリで対比できる
- タグがPlan/Recordで統一されている
- 「何時間使ったか」だけでなく「満足度」も記録

これは自分がToggl等を使っていて「なぜ予定と一緒に管理できないんだ」と感じた課題から生まれた。

## 壁打ちの流れ（時系列）

### 1. 基本構造の確認

**Q: RecordとPlanの関係は？**

→ 1つのPlanに対して複数のRecordが紐づく可能性がある。例えば「毎日の習慣Plan」に対して、実施した日ごとのRecordが作られる。

**Q: Planなしの独立Recordは許可する？**

→ 許可する。予定外のこと（急な対応、気分転換など）も記録したい。Planと対比して使ってもいいし、ログのみで利用する形でもうまく扱えるようにしたい。

### 2. フィールド設計

**Q: 開始時刻と終了時刻は両方必須？**

→ 常にセットで入力。「今から始める」で開始だけ記録するような「進行中」状態は持たない。基本は終わったら入力するイメージ。後から編集は可能。

**Q: Recordにタグは付けられる？**

→ 付けられる。Planから変換した場合はPlanのタグを継承（コピー）。その後は独自に編集可能。PlanとRecordで同じタグマスタを共有する。

**Q: 満足度以外のトラッカーは必要？**

→ とりあえずは満足度（1-5）のみ。しかも任意。最初から複雑にしない。

### 3. 制約・エッジケース

**Q: Planを削除したらRecordはどうなる？**

→ Recordは残る（plan_id → null）。PlanとRecordは依存関係ではなくリレーションでしかない。片方が消えてももう片方は消えない。

**Q: 同じ時間帯にRecordが重複したらどうする？**

→ 許可しない。Planと同じ設計思想で、1つの時間には1つのPlan/Recordのみ。マルチタスク的なこと（散歩しながら読書など）はタグで表現する。

**Q: 過去のRecordはどこまで編集可能？**

→ いつでも編集可能。ただしPlanと同じようにActivity（履歴）で変更を追跡する。

**Q: 深夜を跨ぐRecordはどう扱う？**

→ MVPでは日跨ぎ不可。ほとんどの活動は1日内で完結するし、跨ぐ場合は2つに分けて記録すればいい。睡眠だけは特別扱いを検討（睡眠時間を設定してその時間だけ日跨ぎ可能にする）。要望が多ければ後から対応。

### 4. UI/UX

**Q: Recordをどこで見る？**

→ カレンダーにPlanとRecordを横並びで表示。Sidebarにチェックボタンがあって、両方/片方を切り替えられる。Record一覧ページも作る（InboxのPlanのような形式）。

**Q: PlanとRecordの視覚的区別は？**

→ 色で区別（Planは黒、Recordは別の色）。アイコンでも識別（Planはチェックマーク、Recordは別のアイコン）。枠線は実装して試してから判断。

**Q: Planからの変換時、時刻はどうする？**

→ Planの時刻をそのままコピー。後からカレンダー上でドラッグして調整すればいい。シンプル。

**Q: 記録するタイミングはいつ想定？**

→ 各活動の直後が基本。その日の終わりにまとめて記録するのもあり。週末にまとめては想定外。

**Q: 記録漏れへの対応は？**

→ 基本は何もしない（ユーザーの自由）。将来的に通知で「PlanがあるけどRecordがない」ことをゆるく促すのはあり。

**Q: 空白時間の扱いは？**

→ 何も表示しない。空白=記入可能、というシンプルな考え方。

**Q: Recordの入力は軽くしたい？**

→ 軽くしたい。必須はタイトル+時刻のみ。入力フォームはPlanと同じInspectorベース。時刻入力はカレンダー上でドラッグが基本、自然言語入力は要望があれば検討。

### 5. 価値・目的

**Q: Recordから得たい気づきは？**

→ 達成感、発見、振り返り、自己理解。視覚的に満足度の傾向がわかること。「思ってたより楽しかった」「思ってたより楽しくなかった」という発見ができること。

## DBスキーマ（確定）

```sql
records
├── id (uuid, PK)
├── user_id (uuid, FK)
├── plan_id (uuid, nullable, FK → plans.id)
├── title (text, NOT NULL)
├── start_time (timestamptz, NOT NULL)
├── end_time (timestamptz, NOT NULL)
├── memo (text, nullable)
├── satisfaction (int, nullable, CHECK 1-5)
├── created_at (timestamptz)
├── updated_at (timestamptz)

record_tags（中間テーブル）
├── record_id (uuid, FK)
├── tag_id (uuid, FK)

record_activities（履歴）
├── id (uuid, PK)
├── record_id (uuid, FK)
├── user_id (uuid, FK)
├── action_type (text)
├── old_value (text, nullable)
├── new_value (text, nullable)
├── metadata (jsonb, nullable)
├── created_at (timestamptz)
```

## 実装計画

### MVP優先度

| 優先度 | 機能                      | 備考                           |
| ------ | ------------------------- | ------------------------------ |
| 1      | DB設計 + マイグレーション | recordsテーブル作成            |
| 2      | RecordのCRUD              | tRPC + hooks（Planをトレース） |
| 3      | カレンダー表示            | 既存カレンダーに追加           |
| 4      | Sidebar切り替え           | Plan/Record表示切替            |
| 5      | Planからの変換            | 複製ロジック                   |
| 6      | Record一覧ページ          | Inbox的なUI                    |
| 7      | 満足度入力                | 1-5スケール                    |

### MVP後

- ストリーク（連続記録日数）
- 週次サマリー
- AIフィードバック（週刊系ツールを参考に）
- 振り返り・集計機能

### 対象外（優先度低）

- タイマー機能（要望あれば検討）
- チーム利用
- データエクスポート
- ネイティブアプリ（PWAで当面対応）
