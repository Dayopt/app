# 時間重なりの DB レベル全面禁止（EXCLUDE 制約）

## 基本情報

- **決定日**: 2026-05-13
- **決定者**: 創業者
- **ステータス**: 承認済み（実装済み）
- **カテゴリ**: アーキテクチャ / プロダクト

## 決定事項

### 概要

`entries` テーブルは planned レイヤーと actual レイヤーそれぞれに `EXCLUDE USING gist` 制約を持ち、同一ユーザー内の時間重なりを **DB レベルで全面禁止**する。これは「同じ時間に複数のことはできない」というタイムボクシング思想を、アプリケーション層ではなくデータベースの不変条件として強制する決定である。

### 決定内容

- 同一ユーザー内で planned range（`start_time`〜`end_time`）の重なりを禁止する
  - 制約名: `entries_no_planned_time_overlap`
- 同一ユーザー内で actual range（`actual_start_time`〜`actual_end_time`）の重なりを禁止する
  - 制約名: `entries_no_actual_time_overlap`
- 両制約とも `deleted_at IS NULL`（soft delete されていない行）かつ両端が NOT NULL の行のみを対象とする
- range は半開区間 `[)` で扱う（隣接する終端と始端の一致は重なりとみなさない）

実装: [`supabase/migrations/20260513000000_entry_two_layer_time_ranges.sql`](../../supabase/migrations/20260513000000_entry_two_layer_time_ranges.sql)（L92-110）

## 背景・理由

### なぜ DB レベルで強制するか

時間の重なり禁止は Dayopt の中核思想である。「実際に何が起きたか」を一意なタイムラインとして記録するため、ある瞬間に対応するブロックは高々 1 つでなければならない。これをアプリケーション層のチェックだけに任せると、並行する書き込み（楽観的更新のリトライ、複数デバイスからの同時編集）でレースが生じ、重なりデータが混入しうる。DB の EXCLUDE 制約は並行トランザクション下でも不変条件を保証する最後の防衛線として機能する。

### 並行活動を記録できないことは意図した世界観

「会議をしながら移動する」のような並行活動は、Dayopt では**記録できない**。Toggl は時間の重なりを許すが、Dayopt は許さない。これは機能不足ではなく、「1 つの時間に 1 つの活動を選び取る（選択型ログ）」というプロダクト決定の帰結である。ユーザーには「今この時間に最も意味のある 1 つ」を選んでもらう。

### 緩和は実質不可逆な一方通行

この制約は **緩める方向には実質不可逆**である。一度でも重なりを許すデータが入ると、その後に制約を再強化しようとしても既存データが制約を満たさず、ADD CONSTRAINT が失敗する。再強化には「どの重なりを残しどれを消すか」というデータ修復判断が必要になり、ユーザーの記録を機械的に削除することになる。この非対称性（強化は容易・緩和からの復帰は困難）ゆえに、緩和は「いつでも戻せる設定変更」ではなく**世界観そのものの変更**として扱う。

導入 migration 自体がこの非対称性を体現している。制約を貼る前に、既存の重なりデータをペアで検出し新しい側を soft delete している（[同 migration L40-72](../../supabase/migrations/20260513000000_entry_two_layer_time_ranges.sql)）。一度重なりを許した状態から制約世界へ移行するには、必ずこのデータ犠牲が伴う。

## 検討内容

### 検討した選択肢

#### 選択肢A: DB レベルで全面禁止（EXCLUDE 制約）- 採用

- **内容**: planned / actual 各レイヤーに `EXCLUDE USING gist` を貼り、重なりを DB の不変条件にする
- **メリット**:
  - 並行書き込みでも不変条件が壊れない
  - タイムボクシング思想がスキーマに明文化される
  - サービス層のチェック漏れがあっても最終防衛線が残る
- **デメリット**:
  - 外部カレンダー同期（重なりだらけの外部イベント）の import が原理的に通らない
  - 並行活動を記録したいユーザーには使えない

#### 選択肢B: アプリケーション層のみで検証 - 却下

- **内容**: サービス層の `ensureNoOverlaps` だけで重なりを防ぐ
- **メリット**:
  - 外部同期などで例外的に重なりを許す余地を将来残せる
- **デメリット**:
  - 並行書き込みでレースが生じ重なりが混入しうる
  - 「思想」がコードに散らばり、スキーマからは読み取れない
- **却下理由**: 中核思想を保証するには不変条件として DB に置くべきで、レース耐性も DB 制約でしか得られない

### 採用理由

時間の一意性は Dayopt の世界観の根幹であり、レース下でも崩れてはならない。EXCLUDE 制約は両者を同時に満たす唯一の手段だった。緩和の不可逆性というコストは、「並行活動を記録しない」という明確なプロダクト決定とセットで受け入れる。

## トレードオフ・既知の制約

- **外部カレンダー同期との衝突**: Google Calendar 等の外部イベントは重なりを前提とするため、そのまま import すると制約違反で弾かれる。外部同期を設計する際は、この制約と必ず正面衝突する。
- **並行活動の非対応**: 同時刻に複数活動を持つユースケースは構造的に表現できない。

## 自動記録モデルとの関係（補足）

[ADR-002（Record機能の設計決定）](002-record-feature-design.md) を経て導入された自動記録モデルでは、actual range が未確定の planned エントリ（`actual_start_time` / `actual_end_time` が NULL）が存在する。これらは actual レイヤーの EXCLUDE 制約の**対象外**になる（WHERE 句が両端 NOT NULL を要求するため）。

そのため、自動記録エントリ同士の二重計上を防ぐ防衛線は **DB 制約ではなくサービス層**にある。`EntryService.ensureNoOverlaps`（[`apps/product/src/features/entry/server/entry-service.ts`](../../apps/product/src/features/entry/server/entry-service.ts) L687-747）は、actual が NULL でも「過去・未スキップ・plan range あり」の planned エントリを **effective actual**（plan range を実績とみなした range）として扱い、その重なりを検証する。

effective actual の定義は [`entry-time-model.ts`](../../apps/product/src/features/entry/domain/entry-time-model.ts) の `getEffectiveActualRange` と、DB 側 `entries_effective` view（[`supabase/migrations/20260610000000_entry_auto_record_model.sql`](../../supabase/migrations/20260610000000_entry_auto_record_model.sql)）で同義に保たれている。

整理すると、重なりの防衛は次の二段構えになる:

| レイヤー                  | 防衛線                                                     | 対象                                        |
| ------------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| 確定済み actual / planned | DB の `EXCLUDE USING gist` 制約                            | 両端が NOT NULL の行                        |
| 自動記録（actual NULL）   | サービス層 `ensureNoOverlaps` の effective actual チェック | 過去・未スキップ・plan range ありの planned |

## 再訪条件

以下のいずれかが現実の要求になったとき、この決定を再評価する。**緩和を選ぶ場合は不可逆性を念頭に置き、移行に伴うデータ犠牲（どの重なりを消すか）を含めて設計すること。**

- 外部カレンダー同期（Google Calendar 等）を実装し、重なりを含む外部イベントの取り込みが必要になったとき
- 並行活動の記録を明確なプロダクト要求として受け入れる方針転換があったとき
