# アカウント操作の再認証を「ユーザーが持っている手段」で分岐する

## 背景・当時の前提

- Google ログインを本番で有効にするにあたり、アカウント設定の 3 操作（パスワード変更・メール変更・アカウント削除）がすべて `signInWithPassword` によるパスワード再認証を必須にしていることが分かった
- Google でのみ登録したユーザーはパスワードを持たないため、この 3 つがいずれも実行不能になる。特にアカウント削除ができないのは「忘れられる権利」（実装の発端は #548）に反する
- 当初これを「Google ユーザーはパスワードを持たないのが問題」と整理したが、Tomoya の指摘で問題設定を修正した。パスワードを持たないことは Google / Apple / 大手 SaaS では当たり前の正常な状態であり、直すべきは**再認証の手段をパスワードに固定していること**と**ログイン手段をユーザーに伝えていないこと**

## 決定と理由

- **ログイン手段に応じて表示と再認証を分岐する**。判定は `app_metadata.providers` を見る pure function に集約する（`user.identities` は session 由来の user に含まれないことがあり不安定）
- **Google ユーザーにメールアドレスを変更させない**。IdP がメールの正本であり、アプリ側で変えると Google 側と不一致になって次回ログイン時の紐付けが複雑になる。Google / Notion / Linear と同じ作法
- **Google ユーザーにパスワードのセクションを出さない**。存在しないパスワードを `••••••••` と偽装表示していたのをやめる
- **アカウント削除の再認証**: パスワードを持つ人はパスワード、持たない人は MFA があれば TOTP、無ければ `DELETE` の明示入力のみ
- **パスワードを設定する導線は出さない**。1 ユーザーが Google とパスワードの両方を持つ状態を積極的には作らない（Tomoya の方針）

## 却下した選択肢と、なぜ捨てたか

- **`reauthenticate()` の nonce（メール 6 桁コード）を削除の再認証に使う**: Supabase の nonce は `updateUser` 専用で、サーバー側の任意処理に転用できない。クライアントが「検証しました」と申告する形にすると検証の意味が無くなる
- **Google ユーザーにもメール変更を許可する**: Google 側のメールと不一致になり、自動リンクの挙動が読みにくくなる
- **削除に必ずメール確認を挟む**: 独自のトークン管理が必要で、今回の規模に対して過大
- **パスワードリセットをサーバー側でブロックする**: メール存在の漏えいを防ぐため画面上は同じ応答にする必要があり、service role 経由の実装が要る。案内文で十分と判断

## 影響・やること

- MFA を持たない Google ユーザーの削除要件は現行より緩くなる。根拠は `DELETE` の明示入力・削除通知メール・セッション奪取時点で他の被害が先に出ること。この判断は `docs/product/specs/auth.md` に明記した
- procedure だけあって未使用だった削除通知メール（`sendAccountDeletion`）を実際に送るようにした
- 削除ダイアログの「30日後に削除・その間は復元可能」という文言が実装（即時 `admin.deleteUser`）と矛盾していたため、実態に合わせて書き換えた。猶予期間そのものを実装するなら別プロジェクト
- 残タスク: GCP Console と Supabase Dashboard での Google provider 設定（未実施）
