# プロダクト原則(体験設計)

[`strategy.md`](../business/strategy.md) の原則を画面と操作に翻訳する設計文書。プロダクト原則そのもの(§4)は strategy.md を正とする。ここでは v1 完成の定義と、それを実現する体験設計を扱う。

- strategy.md(不変)と違い、この文書は**設計が進むたび更新される**
- strategy.md と矛盾する設計はここに書かない。衝突したら strategy.md が優先
- 未決事項は本書末尾の「設計上の未決リスト」で扱う

## v1「完成」の定義

機能が揃ったら完成ではない。**このループが最小摩擦で 7 日間自走したら v1 完成:**

1. 朝(または前夜): ルーティンのゴースト確定 + 数ブロックの計画が **2分以内**
2. 日中: ブロック開始の合図が来る。記録はワンタップ、押し忘れは後から訂正できる
3. 夜: カレンダーを開いた瞬間、今日の予定と実績のズレが見える(操作ゼロ)
4. 週末: ルールベース統計が「来週の 1 つの補正」を提示する
5. この間、アプリの都合の通知・煽りがゼロ

残作業リストは「このループの欠けと摩擦」だけで構成する。あったら良い機能はリストに入れない。

## 全体構成: カレンダーが主役

- コンテンツ領域は常にカレンダー(Day/Week のタイムライン)。各日カラムを **Plan レーン(アウトライン・淡色)と Record レーン(塗り・主役)の2レーン**([ADR-025](./log/2026-07-09-time-model-split.md))で並べ、これが操作ゼロのレビュー面を兼ねる
- 分析の置き場は右サイドパネル。独立したレビューページ・統計ページは作らない([strategy.md §4-10](../business/strategy.md))
- この構成の理由: 予定と実績を同じタイムラインで対にする設計の視覚的ペイオフは2レーンの並びであり、それはカレンダーの上でしか見せられない。LP のスクリーンショット 1 枚で差別化が伝わる絵もこれ

## ズレの3点分散

レビュー機能を1つの部屋にせず、3つの瞬間に分散する。

| #   | 場所                       | 役割                                                                                            | 状態                         |
| --- | -------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------- |
| 1   | カレンダー上の2レーン      | Plan レーンと Record レーンの並びで予定と実績のズレが**操作ゼロ**で見える。今日のズレの一次表示 | 実装済み                     |
| 2   | 右サイドパネル             | 今日/今週の差分、タグ別の傾向。「この作業は予定と記録が1時間ずれている」が分かる場所            | 実装済み(下記の設計論点あり) |
| 3   | 作成時のフィードフォワード | ブロックを置く瞬間に「30分の予定ですが、このタグの直近実績は45分です」と統計が静かに教える      | **未実装。3点の中で最重要**  |

学習が一番転移するのは振り返っている時ではなく、**次の計画を立てている時**。③は過去を責める表示ではなく未来の入力を助ける表示であり、「守れる計画」(strategy.md §2)に最も直結する。

## 右サイドパネル(現状と設計方針)

### 現状

「差分」「振り返り」の2タブ構成。

- **差分タブ** — 予定と実績の diff を事実として見せる。GitHub の diff 表示を参考に作った
- **振り返りタブ** — タグ別の確認・傾向

### 評価

差分タブは just idea 起点だが、**筋が良いので残す**。理由:

- ターゲット(AI を使いこなす知的労働者、中核は開発者)にとって diff は母語。「予定と実績の diff」はズレ＝計器(strategy.md §2)の最も自然な表現
- 「差分 = 今日の事実」「振り返り = 期間・タグの解釈」という役割分担は、証拠ベースの進捗感(strategy.md §4-6)と整合する

### 設計論点(未決)

- **タブ分割か、1スクロールか。** 「開いた瞬間にズレが見える」はタブの初期表示側にしか効かない。上=今日の差分、下=傾向の1スクロール案と、現行2タブ案を実使用で比較する
- **初期表示。** タブを維持する場合、開いた瞬間に見えるのは差分(今日の事実)側
- **1画面で終わる読み物以上にしない。** カスタムレポート・期間指定の複雑なフィルタは足さない(Toggl/RescueTime の領土)
- **成績表化しない。** 点数・ランク・評価ラベルは出さない。事実(時間の伸び、頻度)の提示のみ(strategy.md §4-6)

## 計画する

- タグを押して時間に置く。3 ステップ以内で完了
- ルーティン(繰り返し設定したブロック)は当日にゴーストとして現れ、ワンタップで確定。確定されなかったルーティンもズレデータになる

## 実行する

- ブロック開始・終了の opt-in 通知が合図をくれる(フローに入った人間は時間感覚を失うので、これがないと計画は朝作った飾りになる)
- 記録はワンタップ。押し忘れは後から自由に訂正できる

## つながる(MCP / API)

- MCP / API で全データを読み書きできる。ユーザーのチャット画面で「今これやってるからタグで2時間つけておいて」が動く
- API の書き込みはデフォルトでゴースト経由([strategy.md §4-3](../business/strategy.md))。直接確定の許可は要検討(下記未決リスト)
- 週次にルールベース統計で「来週の 1 つの補正」を提示する(AI 不要)。提示場所は右サイドパネルの振り返り側、表現する数値の定義は [ADR-026](./log/2026-07-10-analytics-expression-policy.md)

## 設計上の未決リスト

- 右パネルのタブ分割 vs 1スクロール(上記)
- 2レーンの視覚表現の磨き込み(Week「予定+記録」の密度対応、差分数字の添え方)
- 作成時フィードフォワードの表示形式(どこに・どのくらい静かに出すか。表現する数値は [ADR-026](./log/2026-07-10-analytics-expression-policy.md) で確定済み)
- ゴーストの視覚表現と有効期限の挙動
- ゴースト経由 API 書き込みの詳細(直接確定を許す `confirmed` フラグの是非、外部カレンダー同期の繰り返しイベントの扱い)
- 予定凍結の「開始直後の猶予」(設けるか、設けるなら時間幅。決定したら[時間不変原則](./log/2026-03-10-time-immutability-principle.md)を supersede する)
- エネルギーマッピング(クロノタイプ)の扱い(v1 スコープに含めるかは保留中)
