# Tags（タグ）

ブロック（Plan / Record）の活動分類。Dayoptにおけるタスク管理の代替（タスクリストは持たない）。

## 現在の振る舞い

- 階層は `parent_id` ベースで親タグ → 子タグの最大2階層（`tags.parent_id`、DB trigger `check_tag_hierarchy` でそれ以上のネストを拒否）。旧コロン記法（例: `仕事:開発`）は廃止済みで、既存データは migration で親子構造へ変換済み（`20260424000000_restore_tag_parent_hierarchy.sql`）
- 各タグにカラー（10色パレット）とアイコンを設定できる
- 1ブロック1タグ（複数タグの付与はしない）。Plan と Record はそれぞれ独立して `tag_id` を持つ
- タグには通常 / アーカイブ / マージ済みの3状態がある（下記「状態モデル」参照）

## 状態モデル

| 状態               | 判定条件               | 役割                                                                                      |
| ------------------ | ---------------------- | ----------------------------------------------------------------------------------------- |
| 通常               | `archived_at IS NULL`  | 選択候補（タグセレクタ・フィルタ）に出る。Plan / Record への新規付与可                    |
| アーカイブ         | `archived_at` が非NULL | 選択候補から消える。新規付与不可。過去の Plan / Record では元の名前・色のまま表示を続ける |
| マージ済み（墓標） | `is_active = false`    | マージ元タグが残す痕跡。UI・アーカイブ一覧のどちらにも出ない                              |

`is_active`（マージ専用）と `archived_at`（アーカイブ専用）は独立した状態で、互いに転用しない（マージ済みタグがアーカイブ一覧に混入しないため）。

## タグのアーカイブ

- サイドバー tag-filter の各タグ context menu「アーカイブ」から実行する。可逆操作なので確認ダイアログは挟まない
- アーカイブすると、タグセレクタ・フィルタ・新規タグ付与などの選択候補から消える
- 親タグをアーカイブすると、まだアーカイブされていない子タグも同じ操作でまとめてアーカイブする（道連れ）
- 過去に作成済みの Plan / Record は、アーカイブ後も元のタグ名・色で表示され続ける（タグ lookup は `archived_at` / `is_active` で絞らない意図的な設計）
- アーカイブ済みタグの新規付与は **DB の command 境界**で拒否する（`assert_active_timeblock_tag_v1` が `DT014` を投げ、TS 側が `TAG_ARCHIVED` へマップする）。UI 経路のサービス層でも同じ検証を先に行い、早期に分かりやすいエラーを返す（多層防御）。DB trigger としては実装しない — command 関数内の明示的なアサーションであり、行の書き込みに暗黙で割り込むトリガーではない
- MCP 経路は TS 側の事前検証を持たず、command 境界だけに委ねる。事前検証が apply RPC より前に走ると、「作成成功 → レスポンス消失 → タグがアーカイブされる → 同じ `operationId` で再送」という再送が誤って拒否されるため（RPC は再送の解決をタグ検証より先に行う）
- 例外: 既存の `tag_id` を変更しない編集（タイトル・メモの訂正など）は許可する。後からアーカイブされたタグを保持したままの編集を壊さないため。**同じ `tag_id` を明示的に渡し直す編集も同様に許可する**（command 境界はタグが変わる時だけ検証する）
- MCP の `tags.list` も既定ではアーカイブ済みを返さない（新規付与の候補集合と揃えるため）。ただし `plans.list` / `records.list` / `entries.list` / `review.get` はアーカイブ済みの `tagId` を返しうるので、その名前を解決するには `includeArchived: true` を渡す。各行は `includeArchived` の値によらず `isArchived` と `archivedAt`（アーカイブ日時、通常タグは null）を持ち、アーカイブ済みは通常タグの後ろに並ぶ。`review.get` はタグ別集計行と `largest_tag_variance` signal 自体にも `isArchived` を直接含めるため、`tags.list` への突き合わせなしでアーカイブ済み分類の時間を判別できる

## アーカイブ済みタグの復元

- サイドバー末尾の「アーカイブ済み」折りたたみセクションから、各タグの復元・完全削除を行う
- 親タグを復元すると、同じアーカイブ操作で道連れになった子タグ（`archived_at` が同時刻のもの）も一緒に復元する
- 子タグだけを個別復元する場合、親がアーカイブ中・マージ済み・削除済みであれば root タグとして復元する（親自体は巻き戻さない）
- 同名の通常タグが既に存在する場合は復元を拒否し（`DUPLICATE_NAME`）、リネームしてからの再復元を促す。自動サフィックスでの解決はしない。この判定は子タグに触れる前に行うので、拒否された時はタグが 1 件も復元されない
- アーカイブ済みタグは名前の一意制約から除外されるため、アーカイブ中は同名の新規タグを作成できる
- 復元は子タグを先に、親タグを最後に処理する。途中で失敗しても親はアーカイブ済みのまま残るので、**もう一度復元すれば残りが復元される**（復元済みの子は二重処理しない）

## タグの完全削除

- 通常タグの context menu、アーカイブ済みタグの「アーカイブ済み」セクションのどちらからも完全削除できる。関連する Plan / Record の件数を示す未分類化の説明つき確認ダイアログを挟む（destructive）
- 削除はタグ行の DELETE のみ。関連する Plan / Record は `plans.tag_id` / `records.tag_id` の FK（`ON DELETE SET NULL`）により未分類（`tag_id = NULL`）になる。時間データそのものは消えない（連鎖削除は存在しない）
- 通常の子タグ（アーカイブされていない子）は削除時に root へ昇格する。アーカイブ済みの子タグは FK で `parent_id` が NULL になり、root 化した状態でアーカイブに残る
- 関連する Plan / Record が0件の未使用タグは、確認ダイアログなしで即削除する

## 未分類（tag_id = NULL）ブロックの扱い

タグ削除（前節）で Plan / Record が `tag_id = NULL` になった状態を指す。UI 全体で見せ方・集計への算入可否を次の通り統一する。

- 表示名: カレンダーのカード・Inspector・検索結果では「タグなし」、Review の集計行では「未分類」
- アイコン: 通常のタグ色・アイコンを持たせず、中立マーカー（`TagIcon` の `isUncategorized` prop、`bg-muted` + `Minus`）に統一する。タグは実在するが色/アイコンが未設定のケースとは区別する — `tagColor` / `tagIcon` の null 判定だけでは両者を見分けられないため、呼び出し元が `tagId` の実在シグナルから `isUncategorized` を明示的に渡す
- サイドバー tag-filter の「タグなし」行（`showUntagged`）で未分類ブロックだけを表示/非表示にできる。他のタグの「このタグだけ表示」を選ぶと未分類は自動的に非表示になり、「タグなしだけ表示」を選ぶと他のタグは全て非表示になる（対称）
- 未分類はすべての画面・API の集計に含める。例外はない。集計から外すと、タグを削除するたびに過去の時間が振り返りから目減りするため

| 画面                       | 未分類 | 理由                                                                                                                                                                                                                                                                                                                                             |
| -------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| カレンダー表示・フィルター | 含む   | 実際に確保した時間を欠落なく表示する（`useCalendarFilterStore` の `matchesTagFilter`）                                                                                                                                                                                                                                                           |
| Review の Time P/L         | 含む   | 予定/実績の時間合計を欠落なく比較する。`isUncategorized` 付きの行として表示する（`TimePLTagMarker`）                                                                                                                                                                                                                                             |
| 見積もり精度（タグ別）     | 含む   | タグ削除後も過去の見積もり実績を振り返りから目減りさせない。`tag_id` が null、または削除済みタグ参照（`tagsById` に存在しない）の Plan を単一の未分類バケットへ畳んで集計する（`estimation-accuracy.ts` の `aggregatePlanRecordEstimationAccuracy`）。Time P/L の `buildTagPL` と同じ畳み方                                                      |
| MCP の review context      | 含む   | AI クライアントに渡す合計を画面と一致させる。`timeblock-review-client.ts` はタグ有無で絞らず、`deriveTimePLReview` が `tagId: null` を単一バケットへ畳む。公開契約では `tagId: null` + `isUncategorized: true` の 1 行として返し、`basis.rowFilter` も `active_start_in_period` を名乗る（破壊的変更のため MCP `schemaVersion` を 1→2 に上げた） |

## 関連する意思決定

- タグアーカイブと削除時の未分類化の設計方針を決めた（削除済み、git 履歴参照）（archived_at 新設・is_active 転用しない理由・削除時の連鎖削除廃止）
- 機能スコープ: やらないことを決める（削除済み、git 履歴参照）（ToDo管理・Kanban等を採用しない理由）
