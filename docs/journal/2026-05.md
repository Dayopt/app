#### Claudeの所感

**God module は「外側から剥がす」のが安全**: statistics.ts のような巨大ファイルを分解する際、内側の核（pure aggregation）から先に切り出すと、外側の層（transformer, RPC unpacking）はまだ既存 import で動き続ける。逆順だと、内側の pure を後から切り出す時に外側の層を再書き換えする二重作業が発生する。今日 7 PR で進められたのは順序設計が良かった結果。

**Package の dependency direction は新設時に決まる**: `@dayopt/database` を `@dayopt/billing` より先に新設したのは偶然ではなく、billing が database に依存できるようにする前提。逆順だと「billing を新設したら database への参照経路がなくて型重複した」状態が一時的に発生する。新規 package 追加は「下から固める」原則を毎回適用する。

**Auth boundaries は明示ヘルパーで強制する**: protectedProcedure / publicProcedure の境界が「router 内で if 文で判定」だと、新規 procedure を書く開発者が認可漏れを起こしうる。明示的なヘルパー（`createProtectedProcedure` のような builder）で境界を構造的に強制すると、認可漏れは型エラーで検出可能になる。security skill の責務がコードレベルで担保される形。

## 2026-05-22

### Component から chronotype 計算を除去して hook 化、workspace commands を monorepo-aware にした日

7 コミット。前日の feature-colocation を chronotype 領域に集中させて、Calendar / NowBadge component に残っていた profile 計算を hook 経由に切り替えた。あわせて workspace command を root から一括で呼べる形にし、散在していた public constants を config モジュールに集約。

#### やったこと

- **chronotype hook 化 (3 commits)**: `useChronotypeZones` で Calendar から profile 計算を除去 (#1204)、`useActiveZoneLevel` で NowBadge から profile 計算を除去 (#1205)、`useChronotypeGradient` を `features/chronotype/hooks` へ移動 (#1199)
- **workspace command 整理 (1 commit)**: root から各 workspace を呼べる monorepo-aware な scripts に統一 (#1203)
- **config 集約 (1 commit)**: public constants を `config` モジュールに集約 (#1200)
- **Storybook mock の cleanup (2 commits)**: chronotype mock schema を実型に整合させる (#1197)、ProfileSettings story から dead な `chronotype.get` mock を削除 (#1198)

#### なぜ今日この作業をしたか

前々日から始まった feature-colocation の中で、chronotype だけは「state は store に集約済みだが component が profile から zone を計算する logic を内包」している状態が残っていた。これを hook として切り出すと、Calendar や NowBadge が「profile の生データ」ではなく「zone」や「active level」という抽象を受け取れるようになり、component の責務が UI 表示に純化する。

workspace command の monorepo-aware 化は、apps が 2 つ（product / web）になって packages も増えてきた段階で「個別 workspace に cd して npm 叩く」が現実的でなくなったため。root の `pnpm dev` から product を起動できる、`pnpm build` で全 workspace を build できる、といった形に統一しないと daily な開発フローが破綻する。

Storybook mock の cleanup は、前日の chronotype callback 注入廃止と同じ系統の「dead pattern が新規 story に copy される前に潰す」作業。

#### Claudeの所感

**Component から計算を除去する hook 化は責務の純化**: `useChronotypeZones` のような hook は単なる「ロジックを別ファイルに切り出す」操作ではなく、component が受け取る抽象のレベルを 1 段上げる行為。`profile.timezone.offset` を component が知っているのと `zones[]` を受け取るのとでは、component の認知負荷も変更耐性も違う。hook は「ロジック格納庫」ではなく「抽象の境界」として設計する。

**Workspace command の整備は monorepo の生産性ゲート**: monorepo に移行しても「個別 workspace に入って操作する」フローが残っていると、開発者が「どの workspace でこれを叩くか」を毎回考える認知コストが残る。root の package.json scripts を monorepo-aware に整理する作業は cosmetic に見えるが、これをやらないと monorepo のメリットが daily の操作で打ち消される。

#### やったこと

- **packages 層の新設 (2 commits)**: shared UI primitives package、design token package を workspace に追加 (#1192)。token は package から import する形に統一
- **feature-colocation の量産 (6 commits)**: chronotype state を stores へ (#1190)、calendar view range / precision policy を domain へ (#1186)、calendar interaction の純粋部分を domain へ (#1187)、review variance 計算を domain へ (#1191)、tags 純粋ルールを domain へ (#1193)、entry 時間更新ルールを domain へ (#1185)
- **store の feature ownership 移動 (1 commit)**: `useCalendarFilterStore` を `features/calendar/stores` へ移動 (#1195)
- **chronotype API 整理 (1 commit)**: `onChronotypeChange` callback 注入を廃止し、直接 store を呼ぶ形に統一 (#1196)
- **dead pipeline cleanup (1 commit)**: quality reports 生成を削除 (#1188)
- **docs 集約 (2 commits)**: root docs を集約、packages 設計方針を整理

#### なぜ今日この作業をしたか

前日に entry domain 層を新設した手応えがあったので、同じパターンを他 feature にも展開した。pure logic を domain に切り出すと、test しやすく、UI / server から両方 import 可能になり、feature 境界が明確になる。1 feature ずつ別の日に分けるよりも、同じ思考モードで複数 feature を一気に処理した方が一貫性が出る。

packages 層の新設は monorepo を「単に複数 apps を 1 repo に置く」から「shared 資源を package として切り出せる」段階に引き上げる準備。`ui` と `design-tokens` を最初に切ったのは、これらが apps から最も多く import される下層だから。下層から固めると、後で上層 packages（domain, billing, database など）を追加する際に依存方向が一方向に保てる。

chronotype の callback 注入廃止は、Zustand store を直接呼べる場面で artificial な callback prop を作っていた dead pattern を除去するため。callback 注入は「子 component に親の state setter を見せたくない」場合の defensive な設計だが、store からの値はそもそも globally 取得可能なので、callback で intermediary を作る意味がない。

#### Claudeの所感

**Packages 層は「下から固める」のが安全**: `ui` と `design-tokens` のような最下層 package を最初に切ると、後続の package（domain, billing, etc.）が ui / tokens に依存できる。逆順だと「ui を切り出した時に既存の上層 package が ui を import する形に書き換え必要」となり、変更範囲が大きくなる。

**Feature-colocation は反復が効く**: 同じパターン（pure logic → `features/{feature}/domain`）を 6 feature に適用したが、1 つずつでは「これは本当に正しい切り方か」の判断に時間がかかるところを、3 件目以降は型が固まって機械的に判断できた。この反復の生産性を活かせる日に集中処理するのが効率的。

**Callback 注入の dead pattern は早めに除去する**: defensive な設計として残っている dead pattern（callback 注入、unused prop、no-op wrapper）は、放置すると新規実装で copy されて広がる。1 箇所で見つけたら同様の pattern を検索して同時に潰すのが、技術的負債の伝播を止める最も安いタイミング。

#### Claudeの所感

**直列処理が最速になる場面**: 並列実行できそうな依頼でも、状態が逐次変わるなら直列の方が結果的に速い。今日の dependabot merge では、最初に「5 件並列で rebase 投げて全部 admin merge」を試したが ruleset で全件 reject、その後「全件 rebase → 並列 CI 待ち」に切替えたが 1 件目を merge した瞬間に残り 4 件が再び BEHIND になり 2 度目の rebase が必要に。最初から「1 件 rebase → CI 待ち → merge → 次の 1 件」を直列で回した方が CI 実行時間も無駄にならなかった。並列化の見かけの効率と、状態空間が線形でない作業の本質的な逐次性は区別する必要がある。

**リリースノートの粒度は時間軸を畳むほど粗くなる**: 48 PR を 1 つのリリースノートに圧縮すると、個別 PR の意図は溶ける。Remote MCP server の Phase 1 PoC は #1117 / #1118 / #1121 / #1127 / #1128 の 5 PR に分かれているが、リリースノートでは「MCP server + OAuth 2.1」の 1 項目に圧縮した。圧縮は読みやすさのために必要だが、historical accident を辿りたい人にとっては Full Changelog のリンクが命綱になる。template.md が Full Changelog 必須としているのは正しい判断で、見落とすと future maintainer に大きな負債を残す。

**Conflict resolution はパッチではなく意思決定の保存である**: monorepo branch の merge で「monorepo 側を優先」を機械的に適用すると、main 側で入った INVALID_ENTRY_SHAPE エラーコードが落ちて production が壊れる。逆に「全部 main 優先」を取ると monorepo の two-layer model 改善（future planned で actual を null にする refinement）が消える。Conflict は「2 つの開発系列が独立に正しい判断をした証拠」であり、resolution は「両者の意思決定の上位概念に立って取捨選択を再宣言する」工程。`-X ours` / `-X theirs` のような一括戦略はその責任を回避する手段で、複雑な merge では結局後で崩れる。今日のように conflict ごとに 1 件ずつ理由付きで決める方が、後でレビューする人にも追える形になる。
