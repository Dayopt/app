## 手戻りリスク（確率順）

| 箇所                                        | 確率 | 要点                                                                                                                         |
| ------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------- |
| Entry データモデル（title 廃止 + ゴースト） | ~90% | 最初の外部ユーザーが title 付き entry を作った瞬間、コード変更問題がデータ移行問題に変わる                                   |
| MCP/API の公開契約                          | ~70% | データモデル未確定のまま write API を公開すると API 契約が逆にモデルを固定。write:entries はゴースト schema 確定まで出さない |
| Free/Pro 境界（#1336）                      | ~60% | proProcedure が 20+ 箇所に散在。enforcement 反転前に feature-map の一元化が必要                                              |
| 通知基盤                                    | ~40% | 基盤ごと削除済み。ゴースト確定と UX が絡むのに別々に設計されるリスク                                                         |
| 計測の欠損                                  | ~35% | 手戻りではなく「取り返せない欠損」。計測なしローンチは初期ユーザーの行動データを永久に失う                                   |

**「作って捨てる」サイクルの根本原因**: 戦略の確定より先に実装が走り、更新された理論が過去の実装を否定する（recurrence / 通知 / chronotype / fulfillment / 月次年次 Review / offline-sync / in-app AI で一貫）。防止策は「不可逆度で実装タイミングを分ける」— `[minutes]` な変更（UI・コピー）は理論先行可、`[days]/[irreversible]`（schema・API 契約・価格）はユーザーデータか外部制約の確定まで作らない。

## 1人+AI 体制の構造的死角

1. **AI は理論を反証しない** — 市場データを持たない AI との壁打ちは、検証されていない建物の階数だけを増やす。AI は体系構築という強みの増幅装置であり、市場接触という弱みの補完装置ではない
2. **AI は快適な仕事に吸い寄せられる** — リファクタが摩擦なく進むから 82.4% がインフラ作業になった。250 PR は motion であって progress ではない
3. **ルールが制度化している** — `.claude/rules/plan-format.md` の mandate「launch clock を考慮しない」は PMF 前のステージに不適合。1人+AI 体制では AI ルール = 組織文化
4. **AI は意思決定を強制しない** — ロゴ #1030 が 94 日、#1337/#1336 が 22 日停滞。外部強制関数（ローンチ日の公開宣言、人間の週次報告相手）が必要
5. **「文書 = 成果」の錯覚** — 文書化は AI 協働で最も生産性が高いため、実行の代替物として蓄積される。対抗策: 週1行「今週 repo の外で起きたことは何か」を記録する
