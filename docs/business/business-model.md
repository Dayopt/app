損益分岐点と最適化レバーを特定する。

> 最終更新: 2026-03-19
>
> **注（2026-07-03）**: 本試算は in-app AI 機能があった時点の前提（AI 原価・トライアル AI 利用量）を含む。strategy.md で in-app AI 廃止が確定したため、AI 原価抜きの再計算が必要。再計算は Free/Pro 線引きの決定（未決、[pricing.md](./pricing.md) の全面見直しとセット）と合わせて実施する。

## AI コスト構造

### Free / Trial / Pro モデル

| 状態                    | AI 機能  | モデル       | Dayopt 負担 |
| ----------------------- | -------- | ------------ | ----------- |
| **Free**                | オフ     | —            | **$0**      |
| **トライアル（14 日）** | フル開放 | GPT-4o-mini  | Dayopt 負担 |
| **Pro**                 | フル開放 | ユーザー選択 | BYOK（$0）  |

**設計意図:**

- Free ユーザーの AI コストが**構造的にゼロ**。無料ユーザーが 10 万人いても AI 費用は発生しない
- トライアルは 14 日間 × 新規登録数なので、AI コストの上限が予測可能
- 「AI があるともっと良くなる」をトライアルで体験 → 自然な転換導線

### トライアル AI コスト試算

GPT-4o-mini（Input $0.15/1M tok, Output $0.60/1M tok, ~$0.0003/req）

| 項目                   | 100 人     | 500 人     | 1,000 人   | 5,000 人  |
| ---------------------- | ---------- | ---------- | ---------- | --------- |
| 月間新規登録数（推定） | ~30 人     | ~100 人    | ~150 人    | ~500 人   |
| トライアル中ユーザー数 | ~15 人     | ~50 人     | ~75 人     | ~250 人   |
| 観察イベント/人/14 日  | ~3 回      | ~3 回      | ~3 回      | ~3 回     |
| リクエスト数/月        | 45         | 150        | 225        | 750       |
| **小計**               | **~$0.01** | **~$0.05** | **~$0.07** | **~$0.2** |

> トライアルのみ負担のため、**5,000 人規模でも月 $0.2**。従来の Free Tier 全員開放（$8/月）から **97% 削減**。

### Pro（BYOK）

- Pro ユーザーは自分の API キーで好きなモデル（Claude Sonnet, GPT-4o 等）を使用
- Dayopt 負担: **$0**
- ユーザーの平均 AI コスト: ~$0.3-2/月（使用頻度次第）

### アクティブユーザー限定の観察実行

AI 観察の cron ジョブで `WHERE last_login_at > NOW() - INTERVAL '7 days'` を条件に追加。
ログインしていないユーザーにバックグラウンド分析を回しても結果を見る人がいないので純粋な無駄。

| 指標                        | 全ユーザー対象 | アクティブのみ（7 日以内） |
| --------------------------- | -------------- | -------------------------- |
| 対象率（一般的な SaaS）     | 100%           | 20-30%                     |
| 5,000 人時のリクエスト数/月 | 750            | ~150-225                   |
| 5,000 人時の AI コスト      | $0.2           | **~$0.05**                 |

- **実装**: cron ジョブの WHERE に 1 行追加するだけ
- **復帰時**: ログイン時点から観察を再開。ユーザー体験に影響なし
- **効果**: 登録だけして放置しているユーザーのコストが $0 に。実質コストがアクティブ数に比例する構造

## 最適化レバー

効果が大きい順に整理。

### 1. AI コストの構造的排除（最大インパクト — 実施済み）

- **Free = AI オフ、Trial = 14 日限定、Pro = BYOK** の 3 層構造
- Dayopt の AI 負担はトライアルユーザーのみ（5,000 人でも月 $0.2）
- 「無料ユーザー 10 万人が AI を使いまくる」リスクが**構造的に消滅**

### 2. Supabase Plan 最適化（高インパクト）

- 100 人まで Free Plan で運用可能
- **500 人以下で $25/月節約**

### 3. トライアル AI の効率化（低インパクト — AI コスト自体が極小）

- トライアル中の観察頻度を必要最小限に（14 日間で 3 回程度）
- GPT-4o-mini 固定で単価を最安に維持
- コスト自体が月 $0.2 以下のため、優先度は低い

### 4. check-reminders 最適化（低インパクト）

- 毎分 → 5 分間隔（1,440 回/日 → 288 回/日）
- トレードオフ: リマインダー精度が最大 5 分遅延
- Edge Function コスト **80% 削減**（ただし絶対額は小さい）

### 5. Vercel Edge Runtime 移行（低インパクト）

- Middleware + 軽量 API ルートを Edge Runtime に
- Compute **10-15% 削減**

## 懸念点

### 1. Sentry 移行タイミング

- 初期は Developer Plan($0) で運用。エラー監視 + 基本パフォーマンスは無料枠で十分
- **Team 移行の判断基準**: Session Replay が必要になった時点（本番で再現困難なバグが増えた時）
- 目安: ユーザー ~1,000 人 or 月間エラー数が Developer 枠を超過したタイミング

### 2. Supabase 2 環境問題

- Staging + Production で Pro が 2 つ（$50/月）
- 500 人未満では Staging を Free Plan に留めることで $25 節約
- **ただし** Free Plan は 500 MB DB + API 制限あり

### 3. Stripe 手数料は売上に比例

- $5 × 3.6% = **$0.18/件** は小さいが、年払い $48 × 3.6% = **$1.73/件**
- 年払い比率が高いほど手数料の絶対額が増える
- Stripe の固定費 ¥40/件が $5 の低単価では比率的に重い（~8%）

### 4. GitHub Actions は余裕あるが注意

- 現在 ~400 分/月（無料枠 2,000 分の 20%）
- E2E テスト追加やマトリクスビルドで急増する可能性
- 超過時は $0.008/分（~$8/1,000 分）

## リスク詳細

### Supabase コネクション数

Supabase Free Plan は同時接続数に制限がある（直接接続 60、プール経由 200）。

| Plan                 | 直接接続 | Supavisor プール | 対応ユーザー目安                    |
| -------------------- | -------- | ---------------- | ----------------------------------- |
| Free                 | 60       | 200              | ~100-200 人                         |
| Pro                  | 60       | 200              | ~200-500 人（Compute 追加で拡張可） |
| Pro + Small Compute  | 90       | 400              | ~500-2,000 人                       |
| Pro + Medium Compute | 120      | 600              | ~2,000-5,000 人                     |

- 現在 Transaction mode pooling を使用中（`src/platform/supabase/` 設定済み）
- **対策タイミング**: 500 人を超えたら Small Compute($10/月) の追加を検討
- tRPC バッチリクエストのおかげで 1 ユーザーあたりの同時接続は少ない

### BYOK キー管理

Pro ユーザーの API キーは信頼・法的リスクの問題。

- **保存**: Supabase DB に暗号化保存（`pgcrypto` の `encrypt` / `decrypt`）
- **アクセス制御**: RLS で本人のみ読み取り可、サービスロールで復号
- **利用規約**: キー漏洩時の責任範囲を明記
  - Dayopt はキーの安全な保管に最善を尽くすが、100% の保証はできない旨
  - ユーザーは使用量制限付きのキーを発行することを推奨
  - インシデント発生時の通知義務
- **代替案**: キーをサーバーに保存せず、クライアントから直接 API を叩く設計も検討可能
  - メリット: Dayopt がキーを一切保持しない → 責任ゼロ
  - デメリット: CORS 制約、クライアント側にキーが露出

### ソロ開発の単一障害点

コストの問題ではないが、サービス継続性に直結。

**最低限の自動化**:

- **Sentry アラート** → Slack / メール通知（Developer Plan でも可）
- **Vercel Status** → ビルド失敗時に自動通知
- **Supabase Health** → Edge Function `check-reminders` の失敗検知
- **ステータスページ** → Instatus / Betteruptime 等の無料プラン（$0）で外部監視
  - ヘルスチェックエンドポイント `/api/health` は実装済み
  - ダウン時にユーザーへ自動通知

**対応コスト**: $0（既存ツール + 無料外部監視で対応可能）
