# 公開 docs の情報構造をタスクベースにする

公開 docs（`apps/web/content/docs`）の第 1 階層を、画面名・機能名から「ユーザーがやりたいこと」に変える。

## 決めたこと

- **第 1 階層 = やりたいこと。** `features` / `guides` を廃止し、`plan`（一日を計画する）/ `track`（時間を記録する）/ `review`（振り返る）/ `organize`（タグで整理する）/ `data`（データを外で使う）に分ける。`getting-started` / `troubleshooting` / `faq` は据え置き
- **最大 3 階層。** カテゴリー → ページ、または カテゴリー → グループ → ページ。第 3 階層は見出しではなく独立したページでよい
- **URL は変えない。** ディレクトリはナビ構造だけを決め、URL は決めない。routing の slug はファイル名由来なので、ファイルを移しても `/docs/plans` はそのまま
- **docs は ja 先行にする。** 従来の「en/ja 両方必須」をやめ、ja を正として書き、本文が固まってから en を後追いで揃える。書きかけの ja を追いかけて訳すと、本文が動くたびに 2 倍の修正になる。抜けは `pnpm docs:coverage` が常に一覧するので、追いつく対象を見失わない

## なぜ

**画面名は改名されるが、やりたいことは変わらない。** 同じ日の監査（[docs と LP の突き合わせ](./2026-07-24-docs-lp-coverage-audit.md)）で、公開中の getting-started が実在しない「Stats dashboard」を機能一覧に載せていることが分かった。機能名で切った構造は、製品側の改名や統合のたびに嘘になる。「計画する」「記録する」「振り返る」は製品が生きている限り変わらない。

**検索意図と一致する。** ユーザーは「時間を記録するには」と検索するのであって「Records 画面」とは検索しない。frontmatter の `ai.relatedQuestions` が既に質問形で書かれているのとも揃う。

**3 段上限は深さの問題。** 4 段以上にすると読み手が現在地を見失う。`validate:content` がパスの深さで機械的に止める。

## トレードオフ

**書き手の保守は楽にならない。** 機能ベースなら spec とページが 1:1 だが、タスクベースでは 1 つの機能変更が複数のタスクページに波及する（繰り返し設定の変更が「一日を計画する」と「ルーティンを作る」の両方に効く、など）。楽になるのは読み手側。

これを吸収するため、**内部 spec は機能ベースのまま**にする。`docs/product/specs/` の `public_docs` が spec → 複数 slug の N:M 対応を持ち、`pnpm docs:coverage` が両者を突き合わせる。それぞれの面が得意な軸を持つ形にした。

## URL を変えなかった理由

slug をタスク名に揃えれば一貫性は最高になるが、既存 URL が壊れ、redirect の管理が増える。2026-07-23 のフラット URL 決定を維持し、`[...slug]` catch-all 化もしない。第 3 階層のページを作っても URL は `/docs/<ファイル名>` のままになる。

## 残したもの

**ja 本文の用語が glossary とずれている。** 公開中の docs は「プラン」「レコード」を使うが、製品 UI（`apps/product/messages/ja/calendar.json`、`timeblock.json`）と `docs/product/glossary.md` はどちらも「予定」「記録」。今回はナビ題名を本文の用語に合わせるにとどめ、用語移行は公開 docs 全体（blog・FAQ を含む）に関わるため別作業とする。新規に書いた placeholder は正表記に従い「振り返り」を使う（「レビュー」は glossary の禁止表記）。

`plan` 以外のカテゴリーは、収容ページが draft / placeholder のためまだナビに出ない。本文を書いた時点で自動的に現れる。

## ページ名の付け方

カテゴリー名を繰り返さない。ナビではカテゴリー名の下に並ぶため、「よくある質問 > FAQ: 機能」「困ったとき > 同期・データのトラブルシューティング」のように同じ語が二重・三重になっていた。

- **troubleshooting は症状をそのまま書く。** 「同期されない・データが見えない」「アプリが重い・起動しない」「サインインできない」。ユーザーが検索窓に打つ言葉と一致させる
- **FAQ は主題だけ書く。** 「機能」「料金」「競合との違い」。`FAQ:` prefix はカテゴリー名と重複する
- **機能ページは動詞形にする。** 「予定を立てる」「カレンダーを操作する」。h1 もナビ表示名と一致させる
