# Layer 3: LLM Insights

Layer 1（KPI数値）と Layer 2（パターン検出）のデータをLLMに渡し、自然言語のインサイトを生成・保存・表示する。

---

## 位置づけ

```
Layer 1 (自動計算) — KPI数値の算出
  ↓ データを提供
Layer 2 (パターン検出) — 集計データからパターンや分布を可視化
  ↓ 構造化データを提供
Layer 3 (LLMインサイト) ← 今ここ — 自然言語の気づき生成
```

- **対象ユーザー**: 全ユーザー（Free含む）
- **AI依存**: あり（Anthropic API / Haiku 4.5）
- **データソース**: PostgreSQL RPC関数 → Edge Function → Anthropic API → reflections テーブル → tRPC → UI
- **現在の配置**: Insights タブ

> **Note**: Layer とタブは直交する概念。Layer 3 のインサイトが Review タブに配置される可能性もある。

### Free プランでの位置づけ

インサイトはシステム側のスケジュール実行であり、ユーザーのAIクォータを消費しない。週1回の自動生成なので、月に数回アプリを開くだけでも「先週こうだったんだ」という気づきが得られる。低頻度利用でも価値を感じてもらうための重要な接点。

---

## データフロー

```
Layer 1 (数値)     Layer 2 (パターン)     ユーザー設定
    ↓                    ↓                    ↓
    └────────────────────┼────────────────────┘
                         ↓
              get_insights_data() DB関数
              get_user_settings_for_insights() DB関数
                         ↓
              プロンプトビルダー（Edge Function内）
                         ↓
                    Anthropic API (Haiku 4.5)
                         ↓
                  構造化インサイト JSON
                         ↓
                    reflections テーブルに保存
                         ↓
              tRPC (insights.getInsight)
                         ↓
                  InsightsView で表示
```

## スケジュール生成

Edge Function `generate-reflections` が pg_cron で定期実行し、アクティブユーザーのインサイトを自動生成する。

| 期間 | cron | 実行タイミング | 対象 |
|------|------|-------------|------|
| **週次** | `0 7 * * 1` | 月曜 7:00 UTC | 既存 |
| **月次** | `0 7 1 * *` | 月初 7:00 UTC | 新規 |
| **年次** | `0 7 1 1 *` | 年初 7:00 UTC | 新規 |

**Daily は自動生成しない**。日次粒度選択時は Layer 1 KPI をインライン表示し、「今日の記録を振り返りましょう。週次インサイトは毎週月曜に届きます」と案内。

### コスト

| 期間 | 入力トークン | 出力トークン | コスト/ユーザー | 100ユーザー/月 |
|------|-------------|-------------|----------------|---------------|
| 週次 | ~1,300 | ~500 | ~$0.003 | ~$1.20 |
| 月次 | ~1,500 | ~600 | ~$0.004 | ~$0.40 |
| 年次 | ~2,000 | ~800 | ~$0.005 | ~$0.05 |
| **合計** | | | | **~$1.65/月** |

インサイトはシステム側のスケジュール実行であり、プロダクトの基本機能。

## DB 設計

### reflections テーブル（既存 + 拡張）

既存の `reflections` テーブルを拡張して利用する。

```sql
reflections (
  -- 既存カラム
  id UUID PRIMARY KEY,
  user_id UUID,
  period_type TEXT ('daily', 'weekly', 'monthly', 'yearly'),  -- yearly を追加
  period_start DATE,
  period_end DATE,
  title TEXT,
  activities JSONB,
  insights TEXT,            -- 後方互換用（フラットテキスト）
  question TEXT,
  model_used TEXT,
  prompt_tokens INT,
  completion_tokens INT,
  user_note TEXT,
  created_at, updated_at,
  UNIQUE (user_id, period_type, period_start),

  -- 新規カラム
  structured_insights JSONB,   -- 構造化 LLM 出力
  input_snapshot JSONB,        -- 入力データスナップショット（透明性・デバッグ）
  generation_version INT       -- プロンプトバージョン管理
)
```

### get_insights_data() DB関数

1回の呼び出しで Layer 1 + Layer 2 の全データを返す統合集約関数。

**なぜ単一関数か**: Edge Function は Deno 上で動作し tRPC を呼べない。10+ 個の RPC を個別に呼ぶとレイテンシが増大する。

```
返却データ:
├── Layer 1 KPIs
│   ├── totalMinutes, avgFulfillment, planRate
│   ├── contextSwitches
│   ├── blankRate, estimationAccuracy (avg deviation)
│   └── totalEntries, plannedEntries, unplannedEntries
├── Layer 2 Patterns
│   ├── hourlyDistribution [{hour, hours}]
│   ├── dayOfWeekDistribution [{dow, hours}]
│   └── tagBreakdown [{tagName, tagColor, minutes, entryCount}]
├── Chronotype 分析
│   └── chronotypePhaseBreakdown [{phase, minutes, entryCount, avgFulfillment}]
│       phase: 'warmup' | 'peak' | 'dip' | 'recovery' | 'winddown'
│       ※ ユーザーの chronotype_type + 時間帯マッピングから算出
├── 前期間比較
│   ├── prev_totalMinutes, prev_avgFulfillment, prev_planRate
│   └── (同じ長さの前期間を自動計算)
└── メタ
    ├── daysWithEntries, daysInPeriod
    └── fulfillmentCoverage (スコア記録率)
```

### get_user_settings_for_insights() DB関数

ユーザー設定から LLM プロンプトに必要な情報を取得。

→ chronotype_type, personalization_values, personalization_ranked_values, ai_communication_style, ai_custom_style_prompt, timezone

## Edge Function

**ファイル**: `supabase/functions/generate-reflections/index.ts`

既存の Edge Function を拡張する。

### 主な変更点

1. **マルチ期間対応**: リクエストボディの `period_type` パラメータで週次/月次/年次を切り替え
2. **データ収集の強化**: `get_weekly_reflection_data()` → `get_insights_data()` + `get_user_settings_for_insights()` に置換
3. **プロンプトビルダー刷新**: `buildSimpleReflectionPrompt()` → `buildInsightsPrompt()` に置換
4. **出力パーサー更新**: 新しい構造化スキーマ（InsightOutput）に対応

### プロンプト構造

```
buildInsightsPrompt(insightsData, userSettings, periodType, periodStart, periodEnd)
├── 1. システム指示 + JSON出力フォーマット指定
├── 2. コミュニケーションスタイル（coach/analyst/friendly/custom）
├── 3. ユーザーの価値観（ranked keywords + 12カテゴリ重要度）
├── 4. KPI データ（8メトリクス + 前期間比較）
├── 5. パターンデータ（時間帯/曜日分布、タグ内訳）
├── 6. 期間別の分析フォーカス指示
│   ├── 週次: 即座に行動可能な改善点
│   ├── 月次: トレンド・傾向の特定
│   └── 年次: 大局的な振り返り
└── 7. 出力スキーマ仕様
```

### 異常検知

既存の `checkAnomalies()` はそのまま維持。インサイト生成とは独立して動作し、`burnout_warning` 通知を生成する。

## LLM 出力スキーマ

```typescript
interface InsightOutput {
  /** 要約ヘッドライン (max 80 chars) */
  title: string;

  /** 2-4個の発見 */
  findings: Array<{
    category: 'time_usage' | 'fulfillment' | 'planning' | 'balance' | 'pattern' | 'chronotype' | 'values';
    headline: string;       // max 60 chars
    detail: string;         // max 200 chars
    sentiment: 'positive' | 'neutral' | 'needs_attention';
  }>;

  /** 1-2個のアクション提案（ユーザーの価値観と紐付け） */
  suggestions: Array<{
    action: string;         // max 150 chars
    rationale: string;      // max 100 chars
  }>;

  /** 振り返りの問い (max 200 chars) */
  question: string;

  /** 前期間比較（比較データがある場合のみ） */
  comparison?: {
    summary: string;        // max 150 chars
    direction: 'improving' | 'declining' | 'stable';
  };
}
```

`structured_insights` カラムにこの JSON を格納。既存の `title`, `insights`, `question` TEXT カラムにもフラットに書き込み（後方互換）。

## タグと価値観のマッピング

ユーザーの価値観（ACT 12カテゴリ + ランク付きキーワード）とタグの紐付けは、**LLM推論**で行う。

### なぜ手動マッピングしないか

- タグ数が少ないうちは手動設定がユーザー負担になる
- 価値観の解釈は曖昧で、1つのタグが複数カテゴリに該当しうる
- LLM はタグ名・時間配分・価値観キーワードから文脈を読み取れる

### プロンプトでの指示

```
ユーザーの価値観: [ranked keywords + 12カテゴリ重要度]
タグ別時間配分: [tagBreakdown データ]

上記を踏まえて、ユーザーの時間の使い方が
自身の価値観とどの程度整合しているかを分析してください。
```

> **将来検討**: 利用が進んだ段階で「タグ→価値観カテゴリ」の手動マッピング UI を追加する可能性あり。その場合はプロンプトに明示的なマッピングを渡す。

## エラーハンドリングとリトライ

### 最小データ要件

インサイト生成には最低限のデータが必要。不足時はスキップしてログを残す。

| 要件 | 閾値 | 理由 |
|------|------|------|
| 期間内のエントリ数 | >= 3 | 統計的に意味のある分析のため |
| 記録日数 | >= 2 | 1日だけでは傾向が見えない |
| 合計記録時間 | >= 30分 | 極端に少ないデータでは誤解を招く |

### API エラー時のリトライ

| エラー種別 | 対応 |
|-----------|------|
| Rate Limit (429) | 指数バックオフ（1s → 2s → 4s、最大3回） |
| Server Error (5xx) | 1回リトライ、失敗時はスキップ |
| JSON パース失敗 | そのまま失敗（プロンプトの問題なのでリトライしても無駄） |
| タイムアウト | 30秒で打ち切り、リトライなし |

### 出力バリデーション

LLM の JSON 出力を Zod スキーマでバリデーション。失敗時は `insights` TEXT カラムにフォールバック書き込み（`structured_insights` は null）。

## Feature Boundary

- DB集約（RPC呼び出し、Edge Function）は `reflections` テーブル経由
- tRPC ルーターは `stats` feature が所有（表示ロジック）
- Edge Function はプラットフォーム基盤（`supabase/functions/`）に配置
- AI設定（communication style, values）は `settings` feature 経由で `user_settings` テーブルに保存済み

## Layer 1/2 からの接続点

### プロンプトに含める Layer 1 データ

| メトリクス | プロンプトでの活用 |
|-----------|-----------------|
| Total Time | 活動量の基本コンテキスト + 前期間比較 |
| Avg Fulfillment | 時間の質の評価 + トレンド分析 |
| Plan Rate | 計画実行力の評価 + 改善提案 |
| Estimation Accuracy | 見積もり精度のフィードバック |
| Peak Utilization | chronotype活用度の分析 |
| Context Switches | 集中力パターンの指摘 |
| Blank Rate | 余白の意図性に関する問いかけ |

### プロンプトに含める Layer 2 データ

| パターン | プロンプトでの活用 |
|---------|-----------------|
| 時間帯分布 | ピーク時間帯の特定と活用提案 |
| 曜日分布 | 曜日パターンの指摘（平日/週末の違い） |
| タグ内訳 | 時間配分と価値観の整合性チェック |

### プロンプトに含める Chronotype データ

| データ | プロンプトでの活用 |
|--------|-----------------|
| chronotypePhaseBreakdown | 各フェーズの活用度分析（ピークに集中作業できているか等） |
| chronotype_type | ユーザーのタイプに合わせたアドバイスのカスタマイズ |
