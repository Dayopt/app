# ADR-005: 時間不変原則

> accepted（2026-03-10・遡及記録）

---

## コンテキスト

過去のタイムブロックが自由に編集できる状態は、以下の問題を引き起こしていた：

- 過去の予定時間を変更することで、時間記録としての信頼性が損なわれる（記録改ざんリスク）
- ドラッグ操作で意図せず過去ブロックを移動してしまうUI操作事故が発生
- タイムボクシングの価値（「決めた時間で実行する」）と矛盾する操作が可能だった

Dayoptの核心である「タイムボクシング × 時間記録」の信頼性を保証するために、過去の時間に対する不変性の原則が必要だった。

---

## 決定

「Time waits for no one」原則を採用する。過去ブロックの予定時間（scheduled start/end）は読み取り専用とし、UI disabled + ロジックガードの二重防御で制約を強制する。date関数は全て新インスタンスを返す不変パターンとする。

---

## 詳細

### ブロック状態の判定

時間位置から3状態を自動判定（ADR-001の統合モデルが前提）：

| 状態     | 判定条件                       |
| -------- | ------------------------------ |
| upcoming | `start_time > now`             |
| active   | `start_time <= now < end_time` |
| past     | `end_time <= now`              |

判定関数: `getEntryState()` / `isEntryPast()` — `src/features/entry/lib/entry-status.ts`

### 操作制約マトリクス

**過去ブロック — 禁止:**

- ドラッグ移動、リサイズ、予定時間（scheduled start/end）編集、日付変更

**過去ブロック — 許可:**

- 記録時間（actual start/end）、充実度スコア、メモ、タグ、削除

**未来/進行中ブロック:**

- 全操作可能。ただし未来ブロックを過去の日付へドラッグ移動することは拒否

### 二重防御パターン

各制約はUIとロジックの両レイヤーで防御する：

1. **UI層**: `disabled` 属性、ドラッグハンドル非表示、`minDate` 制約
2. **ロジック層**: `isEntryPast()` による早期return、サーバー側バリデーション

いずれか一方が突破されてもデータの整合性が保たれる設計。

### 不変date関数

`src/lib/date/core.ts` のdate関数群は全て新しいDateインスタンスを返す。入力のDateオブジェクトを変更（mutate）しない。

---

## 結果

### メリット

- 時間記録としての信頼性が保証され、振り返り機能の基盤が堅固に
- UI操作事故（過去ブロックの意図しない移動）が構造的に防止される
- 「時間は待ってくれない」という直感的なメンタルモデルがUXと一致
- 二重防御によりセキュリティ・整合性の両面で堅牢

### トレードオフ

- 「さっき終わったブロックの時間を少しだけ修正したい」というユースケースに対応できない
- 二重防御のメンテナンスコスト（UIとロジックの両方を更新する必要がある）
- active → past の遷移タイミングでのエッジケース処理が必要（操作中に時間が経過した場合）
