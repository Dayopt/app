# コスト最適化分析

ユーザー数 100 / 500 / 1,000 / 5,000 人時点での Vercel・Supabase・Anthropic API の月額コスト試算。
損益分岐点と最適化レバーを特定する。

> 最終更新: 2026-03-19

---

## 前提条件

| 項目 | 値 |
|------|-----|
| デプロイリージョン | Tokyo (`hnd1`) 単一 |
| Runtime | Node.js（Edge Runtime 未使用） |
| Realtime | **未使用**（tRPC + TanStack Query ポーリング） |
| AI方式 | 観察者モデル（バックグラウンド分析、チャット型ではない） |
| AI Free Tier | GPT-4o-mini（最安）、サーバー側定期実行 |
| AI Pro | BYOK（Dayopt 負担なし） |
| 平均エントリ数/ユーザー/月 | ~200 件 |
| 平均 DB 行増加/ユーザー/月 | 800-1,500 行 |
| ストレージ/ユーザー | ほぼなし |

## Anthropic API 内訳（観察者モデル）

チャット型ではなく、**観察者（Observer）**としてバックグラウンドで定期分析を実行。
ユーザーが能動的にリクエストするのではなく、システムが制御する。

**Free Tier モデル選定:**

| モデル | Input/1M tok | Output/1M tok | ~1req あたり | 備考 |
|--------|-------------|--------------|-------------|------|
| **GPT-4o-mini** | $0.15 | $0.60 | **~$0.0003** | Free Tier 推奨。最安 |
| Haiku 4.5 | $0.80 | $4.00 | ~$0.002 | 約 7 倍高い |

| 項目 | 100 人 | 500 人 | 1,000 人 | 5,000 人 |
|------|--------|--------|----------|----------|
| 観察イベント/人/月 | ~5 回 | ~5 回 | ~5 回 | ~5 回 |
| リクエスト数/月 | 500 | 2,500 | 5,000 | 25,000 |
| トークン消費 | 0.75M | 3.75M | 7.5M | 37.5M |
| **小計（GPT-4o-mini）** | **~$0.2** | **~$0.8** | **~$1.5** | **~$8** |

### 観察者モデルの利点

- **GPT-4o-mini で Haiku 比 1/7 のコスト**。観察・振り返り生成には十分な品質
- リクエスト頻度がサーバー側で**完全制御可能** → コスト予測精度が高い
- バッチ処理化で複数ユーザー分をまとめて 1 リクエストにできる
- Pro（BYOK）ユーザーは Dayopt 負担ゼロ

## 損益分岐点

### 仮定

- Pro Plan: **$5/月**
- Free → Pro 転換率: 5-10%
- チャーン率: 5%/月

| シナリオ | 必要 Pro 人数 | 総ユーザー（転換率 5%） | 総ユーザー（転換率 10%） |
|----------|--------------|----------------------|------------------------|
| **損益分岐** ($130) | 26 人 | 520 人 | **260 人** |
| 月 $500 利益 | 126 人 | 2,520 人 | 1,260 人 |
| 月 $2,000 利益 | 426 人 | 8,520 人 | 4,260 人 |

### ポイント

- per user コストが $0.11-0.26 → **$5 でもマージン 90%+**
- 絶対額が小さいためボリュームが必要
- **転換率 10% 達成がキー KPI**（260 人で損益分岐）
- 観察者モデルにより AI 原価が従来チャット型の **1/3 以下**

## 最適化レバー

効果が大きい順に整理。

### 1. 観察者 AI のバッチ化（最大インパクト）

| | 現状 | 施策後 |
|--|------|--------|
| 実行方式 | ユーザーごとに個別リクエスト | pg_cron で定時バッチ（例: 毎日 22:00） |
| 実行環境 | Vercel Function | Supabase Edge Function |
| 削減見込み | — | Anthropic API **50-70%** 削減 + Vercel compute から AI 処理を完全排除 |

### 2. Supabase Plan 最適化（高インパクト）

- 100 人まで Free Plan で運用可能
- cleanup job の保持期間チューニング（`entry_activities` 30 日 → 14 日）
- **500 人以下で $25/月節約**

### 3. 観察頻度の動的調整（中インパクト）

- アクティブユーザーのみ観察（7 日間未ログインはスキップ）
- Free Tier: 週次観察のみ / Pro: 日次観察
- **Anthropic API 40-60% 削減**

### 4. check-reminders 最適化（低インパクト）

- 毎分 → 5 分間隔（1,440 回/日 → 288 回/日）
- トレードオフ: リマインダー精度が最大 5 分遅延
- Edge Function コスト **80% 削減**（ただし絶対額は小さい）

### 5. Vercel Edge Runtime 移行（低インパクト）

- Middleware + 軽量 API ルートを Edge Runtime に
- Compute **10-15% 削減**

## 懸念点

### 1. Sentry 移行タイミング
- 初期は Developer Plan($0) で運用。エラー監視 + 基本パフォーマンスは無料枠で十分
- **Team 移行の判断基準**: Session Replay が必要になった時点（本番で再現困難なバグが増えた時）
- 目安: ユーザー ~1,000 人 or 月間エラー数が Developer 枠を超過したタイミング

### 2. Supabase 2 環境問題
- Staging + Production で Pro が 2 つ（$50/月）
- 500 人未満では Staging を Free Plan に留めることで $25 節約
- **ただし** Free Plan は 500 MB DB + API 制限あり

### 3. Stripe 手数料は売上に比例
- $5 × 3.6% = **$0.18/件** は小さいが、年払い $48 × 3.6% = **$1.73/件**
- 年払い比率が高いほど手数料の絶対額が増える
- Stripe の固定費 ¥40/件が $5 の低単価では比率的に重い（~8%）

### 4. GitHub Actions は余裕あるが注意
- 現在 ~400 分/月（無料枠 2,000 分の 20%）
- E2E テスト追加やマトリクスビルドで急増する可能性
- 超過時は $0.008/分（~$8/1,000 分）

## リスク要因

| リスク | 発生条件 | 影響 | 対策 |
|--------|---------|------|------|
| AI 観察コストスパイク | ユーザー急増時にバッチ未対応 | Anthropic 費用増 | バッチ処理 + 上限設定 |
| DB Storage 肥大 | cleanup 設定漏れ | Supabase 課金増 | pg_cron 監視 |
| Vercel 帯域超過 | 5,000 人+ | 追加帯域費用 | レスポンスサイズ制限 |
| 接続プール枯渇 | 同時接続 1,000+ | クエリタイムアウト | pgBouncer チューニング |
