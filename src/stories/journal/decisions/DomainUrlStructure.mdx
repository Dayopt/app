## 基本情報

- **決定日**: 2026-01-13
- **決定者**: 創業者
- **ステータス**: 承認済み
- **カテゴリ**: 技術/プロダクト

## 決定事項

### 概要

dayopt.app 単一ドメインでLP（Marketing）とアプリを運用。URL構造はusername方式を採用。

### 決定内容

- **ドメイン**: dayopt.app（単一ドメイン運用）
- **LP**: dayopt.app/, /pricing, /about 等
- **アプリ**: dayopt.app/\{username\}, /settings 等
- **方式**: Next.js Multi-zones（2リポジトリ、独立デプロイ）
- **URL識別**: username方式（人間が読める形式）

### URL構造

| パス          | 担当      | 内容                       |
| ------------- | --------- | -------------------------- |
| `/`           | web（LP） | ランディングページ         |
| `/pricing`    | web（LP） | 料金ページ                 |
| `/about`      | web（LP） | アバウトページ             |
| `/blog/*`     | web（LP） | ブログ                     |
| `/{username}` | app       | ユーザーの公開プロフィール |
| `/settings`   | app       | 自分の設定（認証必須）     |

## 背景・理由

### 課題・ニーズ

- LPとアプリで独立したデプロイが必要（Marketing側は頻繁に更新）
- 同一ドメインでのシームレスな体験を提供したい
- ユーザーフレンドリーなURL設計（共有時の見た目が重要）

### データ・根拠

- **市場調査**: GitHub, X, Instagramなど大手SaaSはusername方式を採用
- **ドメイン状況**: dayopt.comは未取得だが、.appドメインで十分（Linear等の成功例）

## 検討内容

### 検討した選択肢

#### 選択肢A: サブドメイン分離

- **内容**: `app.dayopt.app`（アプリ）、`dayopt.app`（LP）
- **メリット**: 完全独立、設定シンプル
- **デメリット**: `app.dayopt.app` は冗長（appが2回）
- **リスク**: 低

#### 選択肢B: サブドメイン（www）

- **内容**: `dayopt.app`（アプリ）、`www.dayopt.app`（LP）
- **メリット**: 独立デプロイ、レイテンシなし
- **デメリット**: wwwをLPに使うのは現代では一般的でない
- **リスク**: 低

#### 選択肢C: Multi-zones（採用）

- **内容**: 単一ドメインで2つのNext.jsアプリを運用
- **メリット**: シームレスなURL体験、大手SaaSと同じパターン
- **デメリット**: rewrite経由でレイテンシ追加（50-100ms）、ゾーン間遷移でページリロード
- **リスク**: 中（設定の複雑さ）

#### 選択肢D: 1プロジェクト統合（Linearパターン）

- **内容**: LPとアプリを同じNext.jsプロジェクトに統合
- **メリット**: 最もシンプル、レイテンシなし
- **デメリット**: LP変更でアプリもデプロイされる
- **リスク**: 低

#### 選択肢E: 別ドメイン

- **内容**: `dayopt.app`（アプリ）、`dayopt.com`（LP）
- **メリット**: 完全分離、Notionパターン
- **デメリット**: .comが取れていない、追加コスト
- **リスク**: 低

### 採用理由（選択肢C: Multi-zones）

- 独立デプロイの要件を満たす
- 単一ドメインで統一感のあるURL体験
- username方式のURL（`dayopt.app/tomoya`）が実現可能
- 大手SaaSと同じ技術アーキテクチャ

### 却下理由

- **選択肢A/B**: URL設計の美しさを優先
- **選択肢D**: 独立デプロイの要件を満たさない
- **選択肢E**: .comドメイン未取得

## 影響範囲

### ステークホルダー

- **影響を受ける**: 開発者（両リポジトリ）
- **協力が必要**: なし（内部決定）

### 関連システム・プロセス

- **変更が必要な箇所**:
  - webリポジトリ: next.config.jsにMulti-zones設定追加
  - appリポジトリ: assetPrefix設定、usernameバリデーション実装
  - Vercel: ドメイン設定
- **影響を受ける機能**: ルーティング、認証、ユーザー登録

## 追加決定事項

### LP側の認証表示

| ボタン                  | 表示    | 理由                                                             |
| ----------------------- | ------- | ---------------------------------------------------------------- |
| ログイン / サインアップ | ✅ 表示 | 新規・既存ユーザーの入り口                                       |
| マイページ              | ❌ 不要 | 他のSaaSもやっていない。LPは入り口、ログイン後はアプリ側に任せる |

### 予約パスの管理

usernameとして登録できないパスを管理する。

**初期リスト**:

- `/pricing`, `/about`, `/blog`, `/terms`, `/privacy`, `/contact`
- 今後LPにページ追加時は随時追加

**管理場所**: appリポジトリの定数ファイルで一元管理

**バリデーション**: ユーザー登録時に予約パスとの衝突をチェック

## 実装計画

### タスク

- [ ] 予約パスのリスト作成（LP側のパスを確定）
- [ ] webリポジトリのMulti-zones設定（next.config.js）
- [ ] appリポジトリのassetPrefix設定
- [ ] username登録時のバリデーション実装（予約パス除外）
- [ ] Vercelドメイン設定確認

### 成功指標

- **定量指標**: LP→アプリ遷移のレイテンシが200ms以内
- **定性指標**: URLが直感的で共有しやすい

## リスク・対策

### 予想されるリスク

1. **レイテンシ増加（50-100ms）**: 許容範囲内。p95目標（300ms）を超えないよう監視
2. **ゾーン間遷移でリロード**: LP→アプリ遷移は初回のみなので許容
3. **予約パス衝突**: usernameバリデーションで防止

### ロールバック計画

- Multi-zonesが問題なら、サブドメイン方式（選択肢B）に切り替え可能
- URL設計の変更は早期段階なので影響は限定的
