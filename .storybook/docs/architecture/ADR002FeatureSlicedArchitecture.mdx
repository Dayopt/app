# ADR-002: Feature-Slicedアーキテクチャ

> accepted（2026-02-26・遡及記録）

---

## コンテキスト

コードベースの成長に伴い、feature間の暗黙的な依存が増大していた：

- あるfeatureのhooksが別featureの内部モジュールを直接importし、変更の影響範囲が不明確
- 循環依存が発生しやすく、ビルド時のtree-shakingが効かないケースがあった
- 新規メンバーがどのモジュールを使ってよいか判断できなかった

Feature-Sliced Design（FSD）の思想を参考に、Dayoptの規模に適した境界設計が必要だった。

---

## 決定

4層のDAG（有向非巡回グラフ）によるfeature境界を導入し、barrel export強制とComposition Layerで層間の依存を制御する。ESLintルールとratchetスクリプトで違反の増加を自動ブロックする。

---

## 詳細

### 階層モデル

```
Layer 0 (基盤):    tags, chronotype       ← 他featureに依存しない
Layer 1 (中核):    entry                  ← Layer 0 の barrel を使える
Layer 2 (体験):    calendar, stats, ai, search ← Layer 0+1 を使える
Cross-cutting:     settings               ← 全feature の barrel を使える
Independent:       auth, notifications    ← 他featureに依存しない
```

上位層 → 下位層のbarrel import のみ許可。同層間・逆方向の参照は禁止。

### Barrel Export

各featureの `index.ts` が公開API。`@/features/entry/hooks/*` のようなdeep importは禁止し、`@/features/entry` からのnamed exportのみ許可。

### Composition Layer

feature間の協調が必要な場合はComposition Layerで統合する：

| 層                   | パス                                       |
| -------------------- | ------------------------------------------ |
| Logic Composition    | `src/app/*/_composition/`                  |
| Layout Composition   | `src/shell/layout/`                        |
| Provider Composition | `src/shell/providers/`                     |
| Shell State          | `src/shell/stores/`, `src/shell/contexts/` |

### 自動検証

- `eslint.config.mjs` の `no-restricted-imports` ルールでビルド時に違反を検出
- `scripts/check-feature-boundaries.ts` がratchetパターンで違反数の増加をブロック
- `.feature-boundary-budget.json` で現在の違反数を管理（現在ゼロ）

---

## 結果

### メリット

- feature内部の変更がbarrel exportを変えない限り外部に影響しない
- 依存方向が明確になり、変更の影響範囲を事前に把握可能
- 新規featureの追加時に適切な層への配置が自動的に決まる
- ratchetパターンにより、既存違反を段階的に解消しつつ新規違反を防止

### トレードオフ

- barrel exportの維持コスト（新しいhooksやコンポーネントを追加するたびにindex.tsの更新が必要）
- Composition Layerを経由するため、feature間連携のコードパスがやや冗長になる
- 初期の既存コードの大規模リファクタリングが必要だった
