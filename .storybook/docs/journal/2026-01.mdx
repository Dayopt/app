#### Record機能とは

#### なぜフォントウェイトを2段階にしたか

| 変更前                 | 変更後          |
| ---------------------- | --------------- |
| 400/500/600/700        | 400/600         |
| 4段階で選択に迷う      | 2段階で迷いなし |

#### なぜIntercepting Routesを採用したか

| 従来の方法               | Intercepting Routes          |
| ------------------------ | ---------------------------- |
| モーダル開閉をstate管理  | URLでモーダル状態を表現      |
| ブラウザ戻るボタン非対応 | 戻るボタンでモーダルを閉じる |
| リンク共有不可           | モーダル状態をURL共有可能    |
| SEO対象外                | 独立ページとしても機能       |

Next.js 13+のIntercepting Routesパターンを採用。モーダルがURLに紐づくことで、「戻る」でモーダルを閉じる、URLを共有して特定のモーダルを開く、といった自然なブラウザ体験が実現できる。

#### Claudeの所感

**「URLファースト」の設計思想:**
タグモーダルをIntercepting Routesに移行したのは大きな判断。state管理からURL管理に移行することで、アプリがより「Webらしく」なった。ユーザーは戻るボタンでモーダルを閉じられるし、URLをコピーして他の人と共有もできる。

**Sortable Tree汎用化の価値:**
タグツリーのDnDロジックを汎用コンポーネントとして切り出した。今はカレンダーのタグフィルターだけだが、将来的に他の場所でも再利用できる基盤になる。最初から汎用化するのは過剰設計になりがちだが、適切なタイミングで実施できた。

**unstable_cacheの採用:**
Next.jsのunstable_cache()でタグマスタデータをキャッシュ。「unstable」という名前だが、Vercelが推奨するパターン。初期ロードが速くなり、サーバーコストも削減できる。

todo/doing/done の3段階から open/done の2段階へ。全コンポーネントを新システムに適応させる大規模な作業日。

#### やったこと

**ステータスシステムの簡略化**

- `todo/doing/done` → `open/done` の2段階に変更
- 「doing」を廃止し、シンプルな完了/未完了モデルへ

**全コンポーネントの適応（14コミット）**

- Calendar: ビュー、フック、サイドバー（Todo→Openリネーム）
- Inbox: テーブルビューを新ステータスに適応
- Board: カンバンボードを新ステータスに適応
- その他: 残り機能すべてを適応

**Inbox再構築**

- ボードビューを削除、テーブルビューに統一
- ルーティング再構築、タブ式サイドバー追加

**UI改善**

- 睡眠統計カード追加（stats）
- 検索機能改善：インライン展開パターン導入
- カレンダー: スケルトン、モバイルタッチヒント、複数日位置表示
- ホバー下線、ステータストグル追加

**その他**

- Claudeコマンド整理（skills → commands）
- `/daily-review` スキル追加（日次振り返り自動化）

#### なぜ2段階にしたか

| 3段階の課題           | 2段階のメリット     |
| --------------------- | ------------------- |
| 「doing」の判断が曖昧 | open/doneで迷いなし |
| 状態管理が複雑        | シンプルな実装      |
| UIも複雑になる        | 直感的な操作        |

「今やっている」を表現したくなるが、実際に運用してみると「doing」に入れるタイミングが曖昧。結局「まだやってない」か「終わった」の2択で十分だった。

#### 大変だったこと

- 変更箇所が多い（全ビューに影響）
- 既存のロジックとの整合性を保ちながらの移行
- 一度に全部変えないとアプリが壊れる状態

#### Claudeの所感

**「引き算」の決断:**
機能を減らす決断は、追加より難しい。3段階→2段階は一見「機能削減」に見えるが、実際はユーザー体験の向上。「doing」という中間状態がなくなることで、ユーザーは「やるか、やらないか」に集中できる。

**大規模リファクタリングの勇気:**
14コミットにわたる大規模な変更は、途中で心が折れそうになる。でも「一度に全部変えないと壊れる」タイプの変更は、覚悟を決めてやり切るしかない。今日やり切ったのは大きい。

**Inboxの統一:**
ボードビューとテーブルビューの2つがあった状態から、テーブルビューに統一したのも「引き算」の判断。選択肢が多いことは必ずしも良いことではない。一つの方法を磨く方が、ユーザーにとってわかりやすい。

### Tags機能Inbox化と業界標準UIへの統一

Tags機能を大幅リファクタリングし、Inbox・Table・Boardすべてで業界標準のUIパターン（Linear、Notion）を採用した集中作業日。22コミット。

#### やったこと

**Tags機能の全面リデザイン**

- サイドバー廃止 → Inbox風の単一カラムレイアウトに変更
- ルートを `settings/tags` に移動
- Inspectorによるタグ作成機能を実装
- グループ表示モードでのタグ作成を有効化
- TagsTableEmptyStateコンポーネント追加
- フィルタ・設定をDropdownMenu UIに統一

**Inbox機能の強化**

- Linear風2カラムフィルターUI実装
- Notion風ソートUI実装（永続化＋動的ソート対応）
- CompactDayViewにカレンダーピッカーとインスペクター統合
- 睡眠時間表示と折りたたみ機能追加
- 一括ステータス変更機能とタブカウントバッジ追加
- InboxSettingsContentをDropdownMenuデザインに変更

**Table機能の改善**

- 動的ページサイズとページネーション簡略化
- 検索入力の安定性向上（ローカルstate + debounce）
- 検索クリアボタンにtooltip追加

**その他**

- Empty Stateを業界標準に沿って再設計
- KanbanボードのカラムにEmpty State追加
- レイアウト・ナビゲーション周りの修正
- ブランド：本能マッピングとターゲット定義を追加

#### なぜ「業界標準」に寄せたか

| 独自UIの問題     | 業界標準のメリット       |
| ---------------- | ------------------------ |
| 学習コストが高い | ユーザーが既に知っている |
| 「なんか違う」感 | 安心感・信頼感           |
| 自分で考える時間 | 検証済みパターン         |

GAFA-First原則の実践。Linear（フィルターUI）、Notion（ソートUI）という成功しているSaaSのパターンをそのまま採用。独自に考える時間をゼロにして、実装に集中できた。

#### 大変だったこと

- Tags機能の構造変更が広範囲に影響（サイドバー削除 → 全体レイアウト再構築）
- 複数の機能を同時並行で改善（Tags、Inbox、Table、Board）
- 22コミットという量の多さ

#### Claudeの所感

**「サイドバーを捨てる」決断:**
Tags機能にサイドバーがあったが、Inbox風の単一カラムに変更した。サイドバーは「情報を一覧できる」メリットがある一方、「画面が狭くなる」「モバイル対応が複雑」というデメリットも。Inboxで既にうまく機能しているパターンがあるなら、それに統一する方が一貫性がある。

**「業界標準をそのまま使う」の威力:**
Linear風フィルター、Notion風ソートを採用した結果、UIの「正解」を考える時間がゼロになった。「こういうUIにしよう」ではなく「Linearと同じにしよう」。判断が早くなり、実装に集中できる。GAFA-First原則がまさに活きた日。

**22コミットの集中力:**
一日で22コミットは相当な量。ただ、バラバラの作業ではなく「業界標準UIへの統一」という一貫したテーマがあったからこそ、迷わず進められた。テーマが明確だと、作業スピードも上がる。

#### Claudeの所感

**「名前が決まる」の威力:**
BoxLog時代は抽象的な議論が多かったが、「Dayopt」と名前が決まった途端、SNSアカウント、メールアドレス、ドメイン設定といった具体的なアクションが次々と出てきた。名前は単なるラベルではなく、行動を引き出すトリガーになる。

### Record機能の設計壁打ち

Claudeとの壁打ちを通じて、Record機能の設計を固めた。

#### やったこと

- Record機能の設計をQ&A形式で整理（18問以上）
- DBスキーマ、リレーション、UI/UX、エッジケースを網羅
- 決定内容を `journal/decisions/2026-01-06-record-feature-design.md` に記録

#### 壁打ちで決まったこと（抜粋）

| 項目          | 決定                       |
| ------------- | -------------------------- |
| Plan : Record | 1 : N（別テーブル）        |
| 独立Record    | 許可（plan_id = nullable） |
| 時間重複      | 不可（1時間帯に1Record）   |
| 満足度        | 1-5スケール、任意          |

#### 学び：音声入力での壁打ちが意外と良い

今回、音声入力で雑に話しながら壁打ちを進めた。結果として：

- **頭の整理になる**: 声に出すことで考えが明確になる
- **雑でもOK**: Claudeが意図を汲み取って質問を返してくれる
- **記録が残る**: 壁打ち内容がそのまま決定記録になる

「考える → 書く」ではなく「話す → 整理してもらう → 記録」という流れ。定期的にこのスタイルで壁打ちするのは良さそう。

#### Claudeの所感

**壁打ちの価値:**
Record機能は「タイムトラッカーと何が違う？」という本質的な問いから始まった。この問いがなければ、ただTogglのコピーを作るところだった。壁打ちの価値は、自分では問わない問いを投げかけてもらえること。

**「終わってから記録」という設計思想:**
「進行中」状態を持たない、という決断は興味深い。多くのタイムトラッカーは「今から始める」ボタンがあるが、Dayoptは「終わったら記録」。これはログの正確性より「振り返りの習慣化」を優先した判断。

**音声入力の可能性:**
創業者が音声入力で雑に話しながら壁打ちしているのは、一人開発の新しいパターンかもしれない。キーボードで考えるより、声で考える方が自然な人もいる。Dayopt自体も、音声入力対応を検討する価値がありそう。
