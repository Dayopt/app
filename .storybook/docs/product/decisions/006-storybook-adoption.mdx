# Storybook導入

## 基本情報

- **決定日**: 2026-02-03
- **決定者**: 創業者
- **ステータス**: 完了
- **カテゴリ**: 技術 / デザインシステム

## 決定事項

### 概要

コンポーネントカタログとしてStorybookを導入し、AIによる管理で運用を継続する。

### 決定内容

- Storybookを導入（vite builder使用）
- 全UIコンポーネントのStoryを作成
- 運用ルール・チェックリストを整備
- Claude（AI）に管理を任せることで形骸化を防ぐ

## 背景・理由

### 課題・ニーズ

- **認知負荷の増大**: コンポーネント数が増え、頭の中だけで把握できなくなった
- **AIへの指示が曖昧になる**: コンポーネントの仕様が明確でないと、Claudeへの依頼が中途半端になりやすい
- **ドキュメント不足**: どのコンポーネントがどういう状態を持つか、一覧で見れない

## 検討内容

### 検討した選択肢

#### Storybook（採用）

- **内容**: React向けコンポーネントカタログの業界標準
- **メリット**:
  - 情報・ドキュメントが豊富
  - React/Next.jsとの相性が良い
  - デザイントークンも可視化できる
- **デメリット**:
  - 形骸化しやすい（更新されなくなるリスク）
  - 管理コストがかかる

#### 導入しない

- **内容**: コード内のコメントやREADMEで管理
- **メリット**: 追加ツール不要
- **デメリット**: 視覚的に確認できない、Claudeへの指示が曖昧になる
- **却下理由**: 現状の課題が解決しない

### 採用理由

1. **ClaudeがStoryコードを読める**: `.stories.tsx` を読ませることで、コンポーネントの仕様・バリエーションをAIが把握できる。これが最大の決め手
2. **業界標準**: Storybookは事実上のデファクトスタンダード。情報が多く、困ったときに調べやすい
3. **形骸化リスクへの対策**: 「AIに管理させる」運用でカバー。Storyの作成・更新もClaude任せにできる
4. **個人開発との相性**: 1人で運用する分には、最小限のルールで回せる

### 期待する効果（優先順位）

1. **コンポーネントの把握**: 頭の中だけで管理できない状態を解消
2. **Claudeへの指示精度向上**: 「このStory見て」と言えるようになる
3. **デザイントークンの可視化**: colors, spacing, radius等を一覧で確認

## AI × Storybook 運用フロー

```
1. Claudeが .stories.tsx を読む
   → コンポーネントの仕様・バリエーションを把握

2. Claudeがコンポーネントを実装/修正

3. 人間がStorybookを開いて視覚的にレビュー
   → 「ここ直して」とフィードバック

4. 繰り返し
```

**役割分担:**

- **AI**: コードを読む・書く（.stories.tsx含む）
- **人間**: 画面を見る・レビューする

Storyが「コンポーネントの仕様書」として機能し、AI-人間間のコミュニケーションを円滑にする。

## app / web 共通運用

### 方針

- **boxlog-app** のStorybookを正とする（1箇所で管理）
- **boxlog-web** はStorybookを持たない
- webで作業するときは、appのStoryを参照してClaude に指示

### 運用フロー

```
webで作業中:

1. 「appのStorybookのトークン見て」とClaude に指示
2. Claude が boxlog-app/.storybook/stories/ を読む
3. 同じ仕様でwebのコンポーネントを作成
```

### 指示例

```
「boxlog-appのButtonのStory確認して、同じ仕様でwebにも作って」
「appのトークン（colors, spacing）見て、このカラーで統一して」
```

### なぜこの運用か

- Storybookの2重管理を避けたい
- ローカルでClaude が読めればOK（リモートデプロイ不要）
- appとwebで同じUI（Button, カラー等）を使い回したい

## 補足

### 形骸化を防ぐ工夫

- Claudeのスキルとして「Storybook運用ルール」を登録
- コンポーネント追加時にStoryも一緒に作成するルールを徹底
- 「実使用パターンのみ」に絞ることで、メンテナンス対象を最小化
