conventions:

- 環境変数で参照される URL のうち、**spec 準拠で固定値であるべきもの (issuer / resource identifier 等)** は env 経由ではなく定数として hardcode する。env はデプロイごとに変わる値、定数は spec で fix される値という使い分け
- service-role を持つ Supabase client は **必ず narrow した DB 型で型付け**する。`SupabaseClient<Database>` のままでは `from('any_table')` が型エラーにならず、cross-tenant leak の type-level guard が消える。`Pick` で必要なテーブルだけ含む `XxxOnlyDatabase` 型を定義する
- Views / Functions / Enums / CompositeTypes も narrow しないと `db.rpc(...)` や view query が compile を通る。**全 surface を `Record<string, never>` で塞ぐ**まで narrow と呼ばない
- GitHub Environment 名の **case を workflow 側で揃える**。Settings → Environments で表示される文字列をそのままコピーする（`production` ではなく `Production`）。startup_failure は CI run page を開かないと気づきにくいので、workflow 名と repo settings の照合を merge 前に確認する
- pre-launch (= 公開済みユーザーがいない) 段階で route を廃止する場合、**redirect は設けない**。launch 後の URL contract が無いので breaking change ではない。301 redirect を残すと history が増えて将来の cleanup コストになる
- Schema drop 時は **declarative schema (`supabase/schemas/`) のファイルも同時に削除**する。migration だけ追加すると `db reset` 後に declarative state が再生成して drift が起きる
- Feature を rename する時は **barrel 経由ではなく feature ディレクトリごと git mv** する。history 追跡のため。barrel で alias を貼って共存させない (削除前提なら過渡期を持たない)
- spec 違反は code comment で **「Phase X で対処」と明示的に deferral** する。inline で fix せず、Phase scope を膨らませない判断を残す。後で plan を切る時に code grep で発見できる

learned:

- GitHub Environment は **case-sensitive で workflow 起動時に存在しないと startup_failure**。run log を開かないと理由が見えない。settings で表示される文字列とは別の case を workflow に書くと sliently 全 run 失敗する
- Vercel の rewrite は **CDN cache または Next.js dynamic route との優先順位で効かないケース**がある。`.well-known/*` (静的) は通るが `/mcp` (動的に見える短縮 path) は 404 page (cached) に捕まる挙動を確認。短縮 path を spec で advertise する場合、middleware (proxy.ts) で rewrite する方が信頼できる
- RFC 8414 §3 で **issuer は AS metadata の URL と完全一致する必要**がある。subdomain で AS を稼働するのに issuer を apex にすると client 側で discovery 失敗（mismatch detected）。env 由来の URL をそのまま issuer に流すのは spec 準拠が崩れやすい
- `SupabaseClient<Database>` の generic は table だけでなく **Views / Functions / Enums / CompositeTypes も持つ**。table を narrow しても view / rpc は通るので、cross-tenant leak の type guard を完成させるには 4 surface 全てを `Record<string, never>` で塞ぐ必要がある
- Supabase RLS で **user UPDATE policy は column-level RLS が無いと「自分の row 全列を書き換え可能」になる**。token_hash や scopes のような sensitive column を user に触らせない設計にするには、UPDATE policy 自体を drop して service-role 経由に閉じる方が単純
- pre-launch の段階で route を廃止する判断は launch 後よりずっと自由。Phase 1 PoC で先に「launch 後に廃止する route は launch 前に廃止する」を選んで scope を整理しておく方が、後の負債を作らない

tried_and_failed:

- vercel.json rewrite で `mcp.dayopt.app/mcp → /api/mcp` と `app.dayopt.app/oauth/token → /api/oauth/token` を advertise → production smoke test で 404 page (cached)。rewrite を諦めて metadata と UI の advertise URL を実体 path に変更 (#1128)
- AS metadata の issuer を `NEXT_PUBLIC_APP_URL` 経由で生成 → apex (`dayopt.app`) になり subdomain (`app.dayopt.app`) で稼働する AS と issuer mismatch。env 依存をやめて hardcode に変更 (#1127)
- service-role client を `SupabaseClient<Database>` で型付けた初版 → `from('entries')` 等が compile を通り cross-tenant leak の type guard が消えた。`Pick` で table を 2 つに narrow → views / functions / enums / composites も narrow しないと rpc / view が通ることが判明し 3 段階で fix (#1121 round 1-3)
- supabase-migration workflow を `environment: production` で参照 → 4 回連続 startup_failure (case mismatch)。`Production` に変更して PoC で追加した 3 migration が production に適用された (#1119)
