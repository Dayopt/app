## 2026-06-08

### 予定だけエントリの表示完全修正と認証セキュリティ強化の日

14 コミット（内 6 件は dependabot 自動更新）。手動実装は entry / calendar / auth の 3 領域。午前は認証セキュリティ修正と EntryCard の UI 改善、午後はカレンダーの「予定だけエントリ」表示バグを根本から修正した。

#### やったこと

- **予定だけエントリの表示修正 (3 commits)**: `entry-adapter.ts` で `actual_start_time` が null の場合 `return null` していた旧実装を削除し、`planned` origin なら `start_time` / `end_time` を表示位置として使うよう変更。`CalendarGridContent` の `overflow-hidden` を `overflow-visible` に変更して予定レイヤーの高さ揃えを修正。`EntryCard` の planned レイヤーがグリッドサイズに揃うようコンポーネント側も調整。テスト追加（`entry-adapter.test.ts` / `EntryRenderer.test.tsx` / `EntryCard.test.tsx`）
- **EntryCard UI 改善 (2 commits)**: 予定ブロックの左上角・左下角を直角化（`rounded-tl-none rounded-bl-none`）。時間表示を左端フラッシュに変更して Day / Week / 複数 View での統一感を確保。Storybook story に時間状態バリアント（predicted / actual / plan-only）を追加
- **認証セキュリティ修正 (2 commits)**: パスワード変更前に `signInWithPassword` で現在パスワードを検証するフローを追加。Supabase の `updateUser` は再認証を要求しないため、ユーザーが意図した変更かどうかを手前で確認する。テスト 142 行追加
- **作成プレビュースタイル統一 (1 commit)**: `DraftEntryBlock` の左アクセントボーダー（`border-l-2`）を削除し upcoming エントリと視覚的に統一
- **依存パッケージ更新 (6 dependabot PRs)**: production 28 件、dev/testing/storybook/linting/types/other の各グループをまとめて更新

#### なぜ今日この作業をしたか

「予定だけエントリ」の修正は、Dayopt の中核的な差別化要素である「計画 × 記録の一体化」に直結するバグだった。ユーザーが事前に予定を入れても（origin: 'planned'）、実際の記録（actual_start_time）がない限りカレンダーに一切表示されない状態が続いていた。これは「タイムボクシングした予定が見えない」という重大な UX の穴であり、計画フェーズでのカレンダー活用を妨げていた。修正は entry-adapter 1 ファイルの null ガード削除が起点だったが、表示崩れ防止のために CalendarGridContent と EntryCard 側の調整も必要で、3 コミットに分かれた。

認証のパスワード再確認は、セキュリティ上の漏れを塞ぐ修正だった。Supabase の `updateUser` は有効なセッショントークンさえあれば現パスワード検証なしで変更できる。この設計は PKCE フローにおける session 継続を前提としており、ウェブアプリの UX では一見問題ないが、「画面ロック中に第三者が操作できる」などのリスクを残す。今回 `signInWithPassword` による現パスワード検証を挟むことで、Supabase が持つ session 継続の仕様に依存せずに安全な変更フローを実現した。

#### Claudeの所感

**「null ガード = 安全」という思い込みが機能バグになる例**: `entry-adapter.ts` の `return null` は「不完全なデータを表示しない」という防御的コードに見える。しかし planned エントリにとって `actual_start_time` が null であることは「エラー状態」ではなく「まだ記録していない正常な状態」だった。型レベルで `planned` origin の場合は `actual_*` が null でも valid であることを表現できていれば、このバグは早期に気づけた可能性がある。DB スキーマと型定義の semantic gap がバグの温床になった事例。

**`overflow-hidden` はレイアウト系バグの隠れた原因になりやすい**: 絶対配置された子要素がグリッドからはみ出ることを期待するコンポーネント（リサイズハンドル、ドラッグプレビュー）には `overflow-hidden` が致命的な影響を与える。今回の修正で `overflow-visible` に変更したが、これはクロスデイドラッグ時に別のはみ出し制御が必要だった旧実装の残骸だった。機能削除時に関連する CSS も一緒に削除するルールの重要性を示している。

**テストのモックビルダーで `null` と `undefined` を区別するパターン**: `makeEntry` 関数で `overrides.actual_start_time ?? entry.start_time` の書き方は、呼び出し元が `actual_start_time: null` を渡しても null を無視して `entry.start_time` にフォールバックしてしまう。`Object.prototype.hasOwnProperty.call(overrides, key)` で「キーが存在するかどうか」を判定することで、null の明示的な指定と未指定を区別できる。テストの表現力に直結するテクニック。

## 2026-06-04

### モノレポ移行後の .claude/ 一括監査と Supabase Preview Branching 導入の日

8 コミット。変更ファイルは 50 本超。午前は Supabase Preview Branching への移行（PR #1256、#1257）、午後は `.claude/` 全体の monorepo 対応監査（PR #1258）を実施。インフラ層と AI 支援層の両方を一日で整備した。

#### やったこと

- **Supabase Preview Branching 移行 (2 commits)**: `supabase/config.toml` を preview branching 対応に更新。`supabase-migration.yml` GitHub Actions ワークフローを廃止し Supabase CLI の preview branch 機能に一本化。Auth SMTP を preview 環境で無効化し、seed をpreview-safe defaults に更新。production migration history の欠損も同日復元
- **.claude/ monorepo 対応 (6 commits → PR #1258)**: `.mcp.json` に playwright・github MCP を追加。`skill/` と `rules/` 全体のパス（`src/` → `apps/product/src/`）、コマンド（`npm run` → `pnpm`）、別リポジトリ参照を一括修正。skill 許可リストの stale エントリ（`less-permission-prompts`）を実名（`fewer-permission-prompts`）に整合。コードレビュー指摘の grep パスと vitest 引数も修正

#### なぜ今日この作業をしたか

Supabase Preview Branching は、PR ごとにマイグレーションを独立した環境で検証できる仕組みで、「本番 DB を直接触らずに migration を確認する」という長期的な安全弁として重要だった。旧来の `supabase-migration.yml` は CI 上で production に直接 push する構造であり、リスクの高い運用だった。移行後は preview branch がマイグレーション確認の主経路となり、production push は明示的な merge 操作のみに絞られる。

`.claude/` 監査は monorepo 移行（単一 Next.js app → apps/product + apps/web + packages/\*）が完了した後に積み残されていたメンテナンス負債の解消だった。旧構造のパス参照が残ったままでは Claude の skill/rules がコードベースと乖離し続ける。今日一括で直したことで、以降の AI セッションで正確なパス案内ができるようになった。playwright・github MCP の追加は、「UI 変更の視覚確認を Claude Code に任せる」「PR 参照を URL コピペなしで取得する」という運用改善の第一歩。

#### Claudeの所感

**AI 支援系の設定ファイルにも技術的負債が積む**: `.claude/` 配下の rules・skills は「AI への指示書」だが、コードと同じく旧構造への参照が残り続ける。今回の監査で 26 ファイル・154 行の変更が必要だったことは、monorepo 移行後の整理が後回しになっていた規模の大きさを示している。AI 支援ファイルは通常のコードと同じ保守コストを持つという認識が必要。

**Preview Branching は「migration を PR レビューで止められる」唯一の構造**: 旧来の GitHub Actions 直 push は「merge されたら即 production 反映」だった。Preview Branching では Supabase の branch merge が別操作になるため、「コードのレビュー」と「DB 変更のレビュー」を分離できる。これは solo dev でも有効で、後日見返す際にも migration の意図が PR に残る。

**Auth SMTP の preview 無効化は見落としやすいトラップ**: Preview Branch はローカル supabase とは別の Supabase project instance を持つが、Auth SMTP 設定はそのまま引き継がれる。preview 環境で実際にメールを送信しようとすると SMTP エラーになる。今回 `config.toml` で明示的に無効化したが、この挙動は Supabase のドキュメントには目立たない形でしか書かれておらず、実際に遭遇して初めて分かる類のものだった。
