decisions:

- MCP server を **Phase 1 PoC** として「OAuth 2.1 (PKCE) + Streamable HTTP `/api/mcp` + `entries.list` のみ」で立ち上げる。Phase 2 以降の write tool は別 plan
- OAuth 2.1 endpoint は `/api/oauth/token`、UI は `/oauth/authorize` + `/oauth/consent`（locale group 直下の独立 OAuth layout）。`(app)` shell（sidebar / calendar 等）に乗せず、ヘッダーレスの薄い chrome で表示
- OAuth metadata (`/.well-known/oauth-authorization-server` + `/.well-known/oauth-protected-resource`) は静的 route で返す。`oauth-server/metadata.ts` に builder を集約
- 既存 `api_keys` テーブルを **撤廃** し `oauth_tokens` に置換。schema 名も `017_tables_api_keys.sql` → `017_tables_oauth.sql` に rename。migration は data 移行も含めて 1 ファイルで（PoC のため過渡期を持たせない）
- `oauth_authorization_codes` は別 migration (`20260501000100`)。code は短命（数分）+ single-use なので tokens と同居させず別 table
- proProcedure は **OAuth bearer token 提示時に必ず DB lookup を行う**（in-memory cache を信用しない）。free / pro plan の判定は entries 取得直前で再評価し、解約直後の token が pro feature を呼ぶ race を塞ぐ
- `entries.list` tool は trpc-bridge (`src/lib/mcp/trpc-bridge.ts`) 経由で既存 `entries.list` procedure を再利用。MCP 専用に business logic を再実装しない
- `lib/mcp/index.ts` の barrel から `trpc-bridge` を **明示的に除外**。trpc-bridge は server-only / route handler 専用で、client bundle に混入させない
- domain は `dayopt.app`（`dayopt.com` ではない）。OAuth metadata の issuer / resource、redirect_uri 検証、Sentry / Vercel 設定すべて `.app` で統一
- vercel.json に rewrite 3 つを追加：`/.well-known/oauth-authorization-server` / `/.well-known/oauth-protected-resource` / `/api/mcp`。Next.js の (locale) prefix を bypass して spec 通りの path で返す
- preview deployment では Upstash 必須 env validation を skip（`NEXT_PUBLIC_VERCEL_ENV === 'preview'` 判定）。preview branch ごとに Upstash を用意せず staging redis を共有 / または rate limit 無効で動かす
- Inspector を **非モーダル化**：overlay backdrop を廃止し、calendar 上で entry を見ながら inspector で編集できる形に。drawer は依然 vaul だが backdrop 透明
- モバイル calendar で **inspector / tag draft の entry を resize 可能** に。draft 状態でも calendar 上の grab handle で時間幅を調整できる
- drawer の close × ボタンは「全 drawer 共通の右上配置」を一度入れた後、**個別 drawer ごとの最適配置に戻す**（inspector は TagRow の「…」menu の隣 / settings は header / etc）。共通化が UX を悪化させると判断
- Inspector の重複チェック（同時刻に既存 entry がある場合の警告）を**復活**。Project B revert と合わせ、tap 即作成系の改善で取り除いていた防御層を戻す
- Project B（tag タップで即作成 α アルゴリズム）を **revert**。直近 1h 履歴 fallback の挙動が不安定で、ユーザー操作と乖離するケースが頻発
- mobile stats フッターの tag chip row は「stats 詳細遷移版」として実装。chip タップで該当 tag の stats 詳細ページに遷移する形（calendar 上の tag filter とは挙動が異なる）
- tags / user_settings の UPDATE policy に `WITH CHECK` を追加。USING だけだと UPDATE 後の row が他 user の行に化けるケースを防げない（Supabase advisor の指摘に追随）

conventions:

- OAuth / MCP の server-only module（DB lookup / token verify / trpc-bridge）は **barrel から明示的に除外**する。client bundle に混入すると secret 取り扱いが破綻するため、barrel re-export を介さず route handler から直 import
- `(oauth)` のような **chrome を共有しない route group** は、`(app)` の sidebar / header layout に乗せず独立 layout を持たせる。OAuth consent / authorize は本体アプリの UX context を引きずらない方が信頼感が上がる
- migration で table を rename / 撤廃する場合、schemas/ 側のファイル名も同時に変える（schemas/ は declarative state なので rename 漏れがあると `db reset` で旧 table が再生される）
- PoC 段階の機能追加は「Phase 1 / 2 / 3 …」で plan を切り、Phase 1 の scope を **「動く最小 + 一切の future-proof を入れない」** に固定する。Phase 2 以降の prep（hook 用の引数、未使用 column 等）も入れない
- Vercel preview deployment は staging と区別される第 3 環境として扱う。preview-only の env 必須性 skip は `NEXT_PUBLIC_VERCEL_ENV` で判定し、staging / production の env 検証を緩めない
- drawer / dialog の close × ボタンは「全 drawer 共通の wrapper 配置」では UX が成立しない場面が多い。各 drawer の content に応じて最適位置を個別決定し、wrapper は close button 自体は提供しない
- Supabase の UPDATE policy では USING に加えて **WITH CHECK を必ず併記する**。USING は更新前 row、WITH CHECK は更新後 row の判定なので、「自分の row しか更新できない」を保証するには両方必要
- domain 表記の統一は CI で自動検出できないので、新規 feature の plan を立てる時に「使う domain は dayopt.app」を明示するのが convention

learned:

- Next.js 15 App Router で `/.well-known/*` を返す場合、`src/app/.well-known/oauth-authorization-server/route.ts` の形で route handler を置けば動く。だが (locale) prefix の middleware が `/.well-known` も capture するので vercel.json の rewrite で素通しさせるか middleware で `.well-known` を除外する必要がある
- `lib/mcp/index.ts` から `trpc-bridge` を re-export すると、client component が誤って barrel 経由で import した瞬間に server-only deps（drizzle / supabase service-role client 等）が client bundle に混入する。barrel に含めない決定が結果として bundle 健全性を保つ
- OAuth 2.1 spec の Authorization Server Metadata は `issuer` と Resource Server Metadata は `resource` がそれぞれ別 endpoint で必要。MCP client (Claude / ChatGPT 等) は両方を well-known で参照するため、片方だけだと client が discover できない
- `oauth_authorization_codes` の TTL は数分（spec 推奨 10 分以内）+ single-use。token と同じ table に置くと cleanup ジョブが TTL 異なるレコードを混ぜて削除する事故が起きやすいので、別 table にして cleanup 戦略を分離する方が安全
- preview deployment は `VERCEL_ENV=preview` で、production / development の二項対立では捉えられない第 3 環境。Upstash や Sentry のように「環境ごとに別インスタンスを用意するのが本来正しい」サービスは preview で skip / shared を選ぶ判断が必要
- 既存 procedure を MCP tool から再利用する場合、tRPC の caller pattern (`createCaller` + ctx 注入) で薄く wrap するのが最も負債が少ない。MCP 専用の business logic 層を作ると将来的に procedure と二重実装になる
- vaul drawer の overlay backdrop を opacity 0 にすると、drawer 内のフォーカス管理は依然動くが、視覚的には「下の content が触れる」ように見える。これが「inspector を見ながら calendar を弄れる」UX になる。完全な non-modal とは違い focus trap は維持されているので tab 遷移は drawer 内に閉じる
- Supabase RLS で UPDATE policy に WITH CHECK を書き忘れると、user_id を他 user の id に書き換える UPDATE が通る。USING は「どの row を更新対象にするか」、WITH CHECK は「更新後の row が policy を満たすか」で、両方必要
